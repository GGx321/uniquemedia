## 0. The plan in twelve lines

1. Stage 4 is **one batch launch**: chosen avatars × videos per avatar → free library photos first →
   generate the rest → montage specs → headless renders → mp4 files in «Готовые видео». No schedule.
2. The click «Запустить: N видео · до $W» **is the acceptance of the launch's worst case** (stage-2
   invariant 4 unchanged). After it the launch spends without further clicks, up to W, and never above.
3. Every paid step goes through the **scene-set path** (CS.4/CS.5), for both values of the scene-review
   switch: compose (writer) → [owner review] → draw in **slices of ≤ 25 photos**. One set per avatar
   per launch, ≤ 100 scenes.
4. W = Σ over avatars of `composeEstimate(n)` + `runEstimateFromScenes(n)`, the engine's own estimate
   functions; the UI only displays what the engine computed.
5. The accepted W is **allocated** per avatar (compose + draw) before the first call; each job's cap is
   its allocation or less. The launch total is a **`Budget` group** (a new `groupOf` limit checked on
   every reserve and hold, §4.10), so «never above W′» is a hard ceiling like the run caps and the
   monthly budget; the orchestrator's own allocation check stays as the second line.
6. The default $10 budget cannot hold a 50-video launch's worst case (≈ $19.20) at once; slices are
   sized to the month's free room (which counts the unspent caps of live jobs), so the launch runs on its
   expected cost (≈ $6.3 by the engine's price list) and pauses with a reason if bad luck exhausts the
   month. The plan screen shows the room against both numbers.
7. Pause and Stop never abort a request: a new **soft stop** (runs and scene jobs) lets the attempt in
   flight finish and starts nothing new.
8. After any restart the launch does nothing until «Продолжить · до $R», a click that accepts the
   launch's remaining worst R (invariant 4).
9. Every video ≤ 10 s, no text layer, always with music (never explicit), stickers per the toggle.
10. Video records gain `origin`/`launchId`/`launchVideoKey` (optional, no schema bump); «Опубликовано»
    and the own-track «для автопилота» flag live in append-only logs, because both records are write-once.
11. Prerequisites P1–P3 (index cost, a cursor for `photos.list`, face-lane priority) land first.
12. Questions Q2–Q5 are with the owner (§17): the no-answer policy, commit + push, the delete default for
    published videos, idle-sleep blocking. The plan carries a recommended default for each, marked
    «pending owner». Q1 (the budget) is now a recommendation, not a question.

## 3. Pipeline and the launch state machine

### 3.1 Decisions that shape the pipeline

**D1. One paid path: the scene set, for both values of the review switch.** A launch never calls
`runs.start`. For each avatar that needs new photos it composes one scene set (writer), then — after
the owner's review when the switch is ON, at once when it is OFF — draws the set in slices. Why:

- the review-ON flow needs the set path anyway (owner decision 7);
- the writer's worst is then fixed per avatar (`composeEstimate(n)` = ⌈n/25⌉ × 2 × the writer ceiling)
  however the draw is sliced, while a sliced `runs.start` would add a writer chunk per slice and make
  the launch's worst depend on budget timing;
- a draw from a set has no writer term, so slices can be any size, and Σ committed (finished slices) +
  Σ cap (live slices) ≤ the draw allocation (§4.3 item 4: a finished slice's slack may be reused);
- one path means one crash matrix to test, not two.

Cost: the writer runs as a `scenes` job one chunk at a time (CS.4a), so photos start later than with a
run's writer phase (an estimate: ~40 s per 25 scenes); the orchestrator overlaps one avatar's compose
with another's draw (§3.5).

**D2. Draw in slices of at most 25 photos, sized to the month's room** (§4.4). One paid draw at a
time per launch, plus at most one compose for a different avatar.

**D3. One set per avatar per launch, at most 100 scenes.** A plan whose generated need for one avatar
exceeds 100 photos is refused at estimate with the reason shown (the default mix needs 90 at 50
videos, §6.2). This is the plan's own limit, not the code's: once the first slice exists the set is
`used`, and the code would allow a second set for the avatar (with review OFF without any extra click).
Multi-set launches are deferred to keep one review round and one crash matrix per avatar.

### 3.2 The launch, per avatar

```
estimate (free) ──click «Запустить · до $W»──► launch file written (ids, allocations)
   per avatar, in parallel where free, one paid draw at a time per launch:
   ┌── library videos: assign photos ─► spec ─► focus prefetch ─► render ─► record ─► done
   └── generated videos:
         compose (paid, set id pre-issued) ─► [review ON: wait for the owner ─ «Продолжить запуск»]
         ─► launch approval (frozen scene list) ─► slice 1..k (paid, ≤ 25 each, run ids recorded first)
         ─► photos arrive ─► assign by category ─► spec ─► focus prefetch ─► render ─► record ─► done
   a video with no fitting track waits (waiting-music) instead of rendering silent
launch done when every video is done or dropped; Stop ends it at any time
```

### 3.3 The launch file — on disk before the first paid call

`<library>/autopilot/<launchId>.json`, written temp + fsync + rename with a growing `revision` (the
scene-set pattern), plus an append-only `<launchId>.log.jsonl` (bounded at 5 000 lines) for the
«Журнал». The library is where the sets, runs, photos and records the launch refers to live; the money
ledger stays in `userData` and is read by the launch's own ids (§4.8).

```
LaunchFile v1 {
  launchId, createdAt, revision,
  draft: LaunchDraft,                 // §9: avatars, videosPerAvatar, mix, categories, poses,
                                      // library, generate, sceneReview, stickers, planSeed
  acceptedMicros,                     // the click
  plannedWorstMicros, plannedExpectedMicros, priceSource, pricesAsOf,   // recomputed at start, ≤ accepted
  status: "running" | "paused" | "done" | "stopped",
  paused:   { reason: "owner" | "restart", at } | null,
  paidHold: { reason: PaidHoldReason, at, detail } | null,     // §4.6
  avatars: [{
    avatarId, phase,                  // §3.5
    allocation: { composeMicros, drawMicros },
    generation: null | {
      sceneSetId, setRunId,           // pre-issued at start
      split: [{ ref, count }],        // the explicit per-category count (§5.3)
      review: boolean,
      autoContinues: { [jobKey]: n }            // §4.6, ≤ 2 per job (a slice run or a scene step)
    },
    videos: [{ key, shape, size, category, source: "library" | "generated",
               photoIds | null, seed,
               music: { source, id, startMs } | null, sticker: { stickerId, anchor, size } | null,
               state, videoId?, dropReason? }]
  }],
  music: { autoRefreshAt?: iso }                // at most one automatic refresh per launch (§7)
}
```

The **set file** stays the source of truth for the approval and the slices (it already has the mutex
and the revision, CS.4a); the launch file mirrors them for display and re-reads them on open. The
track, its `startMs` and the sticker are chosen when the photos are assigned and written with them
(they depend on the library's state, not only on the seed), so a re-submit after a crash renders the
same video.

**Old builds and the strict set file.** `SceneSetFile` is a `strictObject` with a literal
`schemaVersion` (`library/sceneSets.ts:168-170`): the new optional `launchId` and `launchDraw` make a
launch's set unreadable to a build older than Stage 4. Rule, by the T6c precedent (Studio unreleased):
no version bump, the fields are optional, and S4.5a pins that today's set files (without them) still
read and write unchanged.

### 3.4 Ids — what changes in the engine

Today the engine issues every id itself: `runs.start` at `engine.ts:2143`, a set at
`sceneSets/service.ts:309`, the set's run at `service.ts:340`. The contract commands stay as they are.
The orchestrator lives inside the engine and calls the services directly:

- `SceneSetService.compose` gains an **internal** option `{ ids: { sceneSetId, runId }, split, launchId }`.
  The launch issues both ids into its file **before** the call; compose then writes the set file
  (with every chunk's attempt ids) before the first request, as today. After a crash: a set file with
  that id exists → the compose happened (perhaps `stopped`); none readable → the ledger is checked for a
  reserve whose attempt id starts with `<sceneSetId>:` — none means nothing was reserved (the set file
  precedes every reserve) and the same ids are used again; any means the set exists but cannot be read
  (quarantined, unreadable), so the avatar goes to `paidHold { internal }` «набор сцен запуска не
  читается» instead of meeting `ATTEMPT_ID_REUSED` (`budget.ts:173`).
- A **launch approval** (new, S4.5a), under the set's mutex: freeze the ordered list of active scenes
  with text into `set.launchDraw = { launchId, sceneIds, slices: [] }` (the set becomes read-only), then
  per slice append `{ runId, sceneIds, capMicros }` **before** `createRun(runId)`. The first slice uses
  the set's pre-issued `runId`, so `used ⇔ runFolderExists(set.runId)` keeps its meaning. A slice entry
  with no run folder after a crash is created with the same id; `createRun` refuses an existing folder
  (`approve.ts:59-62`), so no step can become two runs.
- Video keys are deterministic (`<avatarIndex>-<n>`); the render carries `{ launchId, launchVideoKey }`
  into its pending intent and record (S4.5c), so a crash between submit and record is resolved by
  provenance, never by guessing from photo usage.
- **The launch registry** (engine memory, S4.5a): `sceneSetId → launchId` and `slice runId → launchId`.
  It feeds the `Budget` group (§4.10), the refusals of §4.7 and the `launchId` marks in `runs.list`. It
  is rebuilt at library open from the readable launch files and their sets' `launchDraw`, before any
  paid command can run, and a slice's entry is added right after the set write and before `createRun`.
  **Unlinked rule:** a set or run whose `launchId` does not name a readable, unfinished launch is treated
  as an ordinary manual set or run by every refusal and every mark (so a removed or finished launch can
  never lock an avatar).

### 3.5 States

**Launch status**: `running` → (`paused` ⇄ `running`) → `done` | `stopped`.
`paused` = nothing runs, paid or free (owner's «Пауза», or any restart).
`paidHold` (only while `running`) = paid work waits for a cause to be fixed; free work goes on.

**Avatar phase**: `planned` → `composing` → `awaiting-review` (switch ON) → `drawing` → `montage`
→ `done`, or `skipped { reason }` (archived, master unusable, failure rate, > 100, blocked).
`waiting { reason }` covers «аватар занят» (another paid job holds it, `engine.ts:3650`), «открыт
набор сцен» (§3.8) and the paid hold.

**Video state**: `planned` → `waiting-photos` → `assigned` → `rendering` → `done`, or
`waiting-music`, or `dropped { reason }` (not enough photos after failures, render failed twice,
avatar gone, launch stopped).

The launch is `done` when every video is `done` or `dropped`. Videos in `waiting-music` keep it
`running` (idle) until a track appears or the owner presses «Стоп».

### 3.7 Pause, resume, stop

- **Soft stop (S4.5b), for both kinds of paid job.** A slice run: no new slot attempt is sent; the
  attempts in flight finish under the normal rules (≤ the 180 s request timeout). A scene job (compose or
  the launch's «Дописать»): the writer attempt in flight finishes and, if accepted, its chunk is saved;
  no new chunk and no new attempt start (a chunk whose first answer was rejected stays pending for the
  next «Дописать», its next unused id). Today a scene job has only the hard cancel, which leaves the
  reserve open (`sceneSets/service.ts:284-293`). **The paid age gate at a stop**: the existing rule
  stays — a paid gate never sends after any stop (`runJob.ts:455-461,518-528`) — so with the image age
  check ON an image that lands during the drain is dropped although it was paid (at most one per
  attempt in flight, ≤ 6). Accepted: the check is OFF by default (stage-2 plan line 34), and an exception
  in that reviewed rule costs more review than ≤ 6 × $0.07 is worth.
- **«Пауза»**: the soft stop; queued autopilot renders that have not started are cancelled (free, their
  photos are released), running renders finish; nothing new starts. Status `paused { owner }`. The card
  reads «Ставим на паузу… N запросов в работе» until the drain ends.
- **«Продолжить · до $R»** (`autopilot.resume { launchId, acceptedRemainingMicros }`): the one click
  that also consents to paid work after a restart, so it carries a sum, like `runs.resume` does
  (`engine.ts:2258-2270`). R = W′ − the launch's committed (settled + open at worst over the launch
  group); the engine recomputes R′ and refuses `PRICE_CHANGED` when R′ > the accepted R (a settle below
  its reserve lowers committed, so a stale screen can ask for less than is left; the UI re-asks).
  **One admission rule** for this click and for every automatic continue (§4.6): `Budget.blocked()`
  (reserves of a previous process, a torn line, a halt — `budget.ts:425-444`) plus the launch's own
  hold reason. Not `paidStop`'s `reconcile` kind: that one turns on for any reserve of this session left
  open (`engine.ts:4052`), even one 180 s timeout, and would make every ordinary Pause → Continue
  demand a reconcile, which refuses `IN_FLIGHT` while any paid job runs. The Autopilot screen therefore
  takes its «Продолжить» state from `LaunchView.resumeBlockedBy`, not from `paidStop`. The click
  re-reads every set and run and picks each avatar up at its persisted step; it never re-plans an
  existing set or run and never raises a cap.
- **«Стоп»**: the same soft stop, then `stopped` (terminal). Generated photos stay in the library as free
  photos; rendered videos stay; unspent allocation is released (bookkeeping only). Each of the launch's
  sets, by phase:
  - `composing` — wait for the soft stop to end, then unlink (below);
  - `awaiting-review`, or written but not approved — unlink;
  - approved (`launchDraw` written) with **no** slice folder yet (e.g. «Стоп» during a `paidHold` right
    after the approval) — under the set's mutex clear `launchDraw` and `launchId` (revision + 1); the set
    becomes an ordinary open set again;
  - at least one slice folder exists — the set stays `used`; its undrawn scenes are not drawn; its runs
    are unlinked (they become ordinary manual runs, resumable by the owner's own click).

  «Unlink» = clear `launchId` under the set's mutex (revision + 1). The set is then the avatar's
  ordinary open set on «Фото» (paid for; drawing or discarding it is the owner's call). Should a crash
  interrupt the unlink, the unlinked rule of §3.4 already treats it as unlinked once the launch is
  `stopped`.
- No autopilot button aborts a request. A hard abort happens only when the process dies (quit, crash).
- **The bypass through «Фото» is closed** (§4.7): while the launch is unfinished, a manual
  `runs.resume`, `runs.cancel`, `scenes.cancel` or `scenes.write { unwritten }` on a launch's run or set
  is refused, so nothing paid can move while the launch is paused.

### 3.8 Window closed, quit, restart, sleep, conflicts

- **Window closed (macOS)**: the app and the engine keep running (`main/main.ts:511-524`); the launch
  goes on; the window reopens from `engine.snapshot` (+ the new `Snapshot.autopilot`). While a launch is
  `running` with work in flight, main holds `powerSaveBlocker.start("prevent-app-suspension")` and
  releases it otherwise (S4.7, after spike SP1). That mode also keeps the Mac from **idle** sleep (not
  lid sleep), which is more than decision 10's «App Nap only»: default ON, **pending owner** (Q5); if he
  says no, S4.7 holds the blocker only if SP1 shows a weaker way to stop App Nap alone.
- **Windows**: closing the last window quits (`main.ts:522-524`) → the quit rules below.
- **Quit (Cmd+Q, or the last window on Windows)**: a native confirmation when a launch is `running`:
  «Идёт автопилот. Если выйти, запуск встанет на паузу. Запросы, которые сейчас в работе (N), прервутся
  и до сверки будут считаться по худшей цене.» — «Выйти» / «Остаться». Today nothing asks
  (`quitFlow.ts:56-88`), and `Engine.shutdown` cancels renders only (`engine.ts:1004-1014`); in-flight
  paid requests die with the process and leave open reserves → `RECONCILE_REQUIRED` at the next start
  (`budget.ts:438-441`). That stays true; the dialog only says it.
- **Any restart** (app relaunch, or the engine's one automatic restart `engineHost.ts:15-19`): every
  `running` launch is read as `paused { restart }`. Nothing — paid, free, or a music request — happens
  until «Продолжить · до $R» (invariant 4; A5). `autopilot.continueAfterReview` during
  `paused { restart }` records the approval (the frozen list, §3.4) and nothing more; the draw waits for
  «Продолжить».
- **Sleep** (lid closed): in-flight requests may get no answer → open reserves at worst (in-session, so
  `Budget.blocked()` does not stop the engine, `budget.ts:438-441`; the UI's `reconcileNeeded` turns on,
  `engine.ts:4049-4061`, but the launch's admission rule ignores it, §3.7). The launch applies the
  no-answer policy of §4.6 (owner question Q2). On
  `powerMonitor` `suspend`, main tells the engine (main-only `host.power`) to stop sending new attempts;
  on `resume` sending continues. Whether those events arrive in time is spike SP1.
- **Library switch**: refused while a launch is `running`, by an explicit launch check (`#paidCommands`
  alone is 0 between two of the launch's jobs); allowed when it is `paused`, `done` or `stopped` — the
  launch stays with its library.
- **Manual work on the same avatar**: one paid job per avatar (`engine.ts:3650`). Whoever comes second
  gets `IN_FLIGHT`; the launch waits («Mia занята») and retries when that job ends, never fails.
- **The owner's own open scene set**: compose refuses (`service.ts:318-324`). The plan marks the avatar
  «открыт набор сцен — завершите или удалите его на экране «Фото»» and «Запустить» stays disabled for a
  plan that needs generation for it (library-only videos for it are fine).
- **Avatar archive/delete during a launch**: deletion is refused while the avatar is in a non-terminal
  launch (new refusal, detail «аватар в запуске автопилота»); an avatar archived while paused is
  `skipped { archived }` on «Продолжить».

## 4. Money

### 4.1 Invariant 4 and the launch click

Stage-2 invariant 4 (`docs/studio/2026-09-24-stage-2-plan.md:81`) stays: the click
«Запустить: N видео · до $W» accepts W, and nothing after a restart is spent without a click. Owner
decision 5 makes explicit what that click covers, and this plan writes it into invariant 4 as a
clarification, not a change:

> Within one engine session, a launch's own jobs (its compose, its «Дописать», its slices, the resume of
> any of them inside its cap) run without further clicks, each with a cap from the launch's allocation,
> all inside the launch's `Budget` group. After a restart nothing of the launch runs until
> «Продолжить · до $R», a click that accepts the launch's remaining worst R. Paid actions on the review
> screen (⟳ «Другая сцена», a rewrite) stay their own clicks with their own price and cap.

The sentence «an interrupted one [scenes job] is offered again as a new command, never resumed
silently» applies to the owner's manual sets. For a launch's set, the launch's acceptance covers its
resume within the compose allocation, in the same session only.

### 4.2 The launch estimate — one function, built on the engine's estimates

The renderer never computes money: it shows what `autopilot.estimate` returns (as every paid screen
does today, `renderer/screens/photos/usePaidAction.ts:8-12`). The engine computes both the preview and
the start with the same code:

- `planLaunch(draft, libraryState, musicState)` — pure (`shared/autopilot/plan.ts`): per avatar the
  videos, shapes, sizes, library assignments and the generated need `n_a` per category.
- `launchEstimate(plan, unit)` — pure (`shared/autopilot/estimate.ts`), linear in the counts:

```
worst_a    = composeWorst(n_a)    + n_a × photoWorst          // = composeEstimate(n_a).worst + runEstimateFromScenes(n_a).worst
expected_a = n_a × writerTypical  + n_a × photoExpected        // = composeEstimate(n_a).expected + runEstimateFromScenes(n_a).expected
W = Σ_a worst_a      E = Σ_a expected_a
composeWorst(n) = ⌈n / 25⌉ × 2 × writerCeiling                 // writerWorstMicros, money/estimate.ts:177-180
```

- `unitPricesOf(book, settings)` — engine side (`engine/autopilot/prices.ts`): `photoWorst` and
  `photoExpected` come from `estimateRun(book, { photos: 1, writer: null, route, attemptsPerSlot: 3,
  ageChecks })` (`money/estimate.ts:192-219`), so the dearer route model and the Seedream fallback
  (`runs/plan.ts:73-77`) and the age-check toggle are priced exactly as a run prices them;
  `writerCeiling`/`writerTypical` come from the set's text model as `composeEstimate` prices it. A
  pinned test asserts, for one avatar and every n in 1..100, `launchEstimate == composeEstimate(n) +
  runEstimateFromScenes(n)` on the same book (A18).
- The mock uses the same `launchEstimate` with fixed unit prices, so its numbers cannot drift either.
- The mockup's own formula (`$0.05 × N` without retries, a writer at $0.07,
  `Autopilot.dc.html` script) is not used.

**Worked example** (estimates; an attempt reserves $0.07 and settled at $0.06 in the CS.7 canary,
owner-decisions money facts; writer ceiling $0.0375 per attempt): one avatar, 50 videos, default mix,
library off → 35 single + 10 collage × 3 + 5 slides × 5 = **90 photos**.
W = 90 × 3 × $0.07 + ⌈90/25⌉ × 2 × $0.0375 = $18.90 + $0.30 = **≈ $19.20**.
E = 90 × $0.07 + 90 × ≈ $0.00045 = **≈ $6.34**. The engine's expected price per photo is the price
list's image price **including the reference input image** (`imageWorstCase` with `refs`,
`money/estimate.ts:154-156,213`; the fallback list's grok entries carry `inputImageMicros: 10_000`,
`money/prices.ts:370-387`), ≈ $0.07, not the measured settle. Real spend tends to come out lower
(≈ $0.06 per attempt, plus retries); every figure the screen shows is the engine's E.

### 4.3 Allocation: Σ allocated ≤ accepted, caps never raised

At `autopilot.start` the engine recomputes the plan and W′ from the current library and prices:

1. `W′ > acceptedWorstMicros` → `PRICE_CHANGED` (free; the UI re-asks the estimate and needs a new
   click, `usePaidAction.ts:8-12`). `W′ ≤ accepted` → accepted; the launch spends at most W′.
2. Per avatar: `allocation.composeMicros = composeEstimate(n_a).worst`,
   `allocation.drawMicros = runEstimateFromScenes(n_a).worst`; Σ_a = W′ ≤ accepted. Written into the
   launch file before anything else; then the launch's **`Budget` group** is registered with cap W′
   (§4.10), still before the first reserve.
3. Compose: `acceptedWorstMicros = allocation.composeMicros`; the compose job's cap is its estimate at
   the call, never above (`service.ts:330-333`, the CS.4a cap rule). A price rise above the allocation →
   `PRICE_CHANGED` → `paidHold { price }` (§4.6). The launch's own «Дописать» after a stop gets only what
   the earlier writer scopes of the set left: `composeMicros − committed(<setId>:writer-*)`
   (§3.6 row 2), never a fresh `writeEstimate` on top.
4. Slice i: size `s` (§4.4); `cap_i = runEstimateFromScenes(s).worst` at the slice's prices, required
   ≤ the **draw allocation left** = `drawMicros − Σ committed(finished slices) − Σ cap(live slices)`
   (a slice is live while it runs or can be resumed; finished once every slot is closed — `runs.resume`
   then refuses, `engine.ts:1996`). Checked under the set's mutex against the slice entries in the set
   file (the source of truth) and written into the entry before `createRun`.
   - price unchanged → Σ cap_i ≤ `drawMicros`, and the slack of finished slices absorbs small rises;
   - price fell → caps are smaller, the leftover is never spent;
   - price rose → the slice shrinks to the largest `s` whose cap fits; `s = 0` → `paidHold { price }`.
     The launch then makes fewer photos and fewer videos, logged «цена выросла: −k фото»; it never asks
     the `Budget` for more.
5. Failed slots are **not refilled** within a launch: a refill would need new scenes (new writer
   money, and, with review ON, scenes the owner never saw). Fewer photos → fewer or smaller videos (§6.4).
6. Two lines of defence. First, the `Budget` group refuses any reserve or hold that would lift the
   launch's committed (settled + open at worst + held, over all its scopes) above W′ — a hard ceiling
   whatever the orchestrator computes. Second, before every allocation the orchestrator recomputes the
   A2 sum from the set files and the ledger; a would-be excess refuses (`paidHold { internal }`).

**A2, restated.** At every moment, Σ over the launch's scopes of (committed for a finished scope, cap for
a live one) ≤ W′ ≤ accepted. Σ of caps alone is not the right quantity: a «Дописать» is a new scope next
to the compose's, and a finished slice spends less than its cap.

The launch never calls anything that raises a cap or the monthly budget (A3); `runs.resume` cannot
raise a cap by construction (`engine.ts:2271-2296`).

### 4.4 The monthly budget

Facts. `#checkMonthlyRoom` (`engine.ts:3820-3827`) refuses a job when
`spent + open reserves + held + the job's whole worst > budget`. `held` is only the in-memory holds of
attempts admitted but not yet reserved (`budget.ts:281`, `:458-464`) — **the unspent rest of running
jobs' caps is not counted**. The month is then enforced per attempt: every `tryReserve` checks
`spent + open + held + this attempt's worst ≤ budget` atomically with the scope cap
(`budget.ts:176-185`); a refusal there is a `limit` failure that stops that slot only
(`runs/failures.ts:31`, `runJob.ts:691,821`), and the run ends `failed` with open slots, resumable. The
month is the UTC calendar month (`budget.ts:106-109`); the default budget is $10
(`main/settingsStore.ts:14`); `settings.setBudget` changes it under the budget's mutex (`budget.ts:266-271`).

So a 50-video launch (W ≈ $19.20) can never pass one `#checkMonthlyRoom` under $10, but its expected
cost (≈ $6.34) fits. **Decision: both.** Sequential slices sized to the room, and the plan screen
shows the room against the launch's needs so the owner can raise his budget in Settings when he wants
the worst case covered. No automatic raise, ever.

- **The room, computed in the engine** (new `Engine.#monthRoom()`, S4.2):
  `room = budget − (spent + open + held + Σ_{live scopes} max(0, cap − committed))`, where the live
  scopes are the caps registered for running jobs (`#caps`, set at launch `engine.ts:2314`, dropped at
  the end `engine.ts:2362`) plus this launch's resumable slices (they will come back). Without the last
  term (r1) a slice sized to the whole room hits the month mid-run whenever another job — the launch's
  own parallel compose, or a manual run — is still holding cap; its resume then needs room for its whole
  remaining worst (up to $5.25, `engine.ts:2287`) and the launch sits in `paidHold { budget }` for want
  of cents. The same `room` feeds `monthFit` and the slice size, so «fits» never claims room a running
  manual job may still take.
- **Slice size** = `min(25, scenes left, ⌊draw allocation left / photoWorst⌋, ⌊room / photoWorst⌋)`.
  25 bounds the held worst (≤ $5.25) and keeps Pause responsive. One draw at a time per launch; the
  network pool is global (`engine.ts:870`), so parallel draws would not be faster anyway.
- **`s = 0` because of the room** → `paidHold { budget }`: «Месячный бюджет: свободно $R, следующей
  партии нужно до $X». Cleared by a raise in Settings or a new UTC month, then «Продолжить».
- **The plan screen** shows «В месяце свободно $R из $B · UTC» next to «Ожидаемая ≈ $E» and
  «Предел запуска · до $W», in one of three states (one function `monthFit`, used by the preview and by
  `autopilot.start`):

| State | Condition | Screen | Start |
|---|---|---|---|
| `fits` | R ≥ W | nothing extra | allowed |
| `fits-expected` | E ≤ R < W | «Хватит, если без повторов. При неудачах запуск встанет на паузу по бюджету. Чтобы такого не было, поднимите бюджет до $⌈W − R + B⌉.» + link to Settings | allowed |
| `short` | R < E | «Бюджета не хватит даже на ожидаемую цену: свободно $R, нужно ≈ $E. Уменьшите число видео или поднимите бюджет.» | disabled; the engine refuses `BUDGET_EXCEEDED` |

Worked example (estimates): $10 budget, nothing spent, the 50-video launch is `fits-expected`
(E ≈ $6.34 ≤ $10 < W ≈ $19.20). Compose ≈ $0.04 spent; slice 1 (25, cap $5.25) fits R ≈ $9.96; after it
≈ $1.5–1.8 really spent (settles ≈ $0.06 per attempt plus retries); slices 2 and 3 fit the same way;
slice 4 (15, cap $3.15) fits R ≈ $4.8. Typical end: ≈ $5.5 really spent. With twice the usual retries
the fourth slice shrinks to the room and the launch pauses near the end of the budget.

The budget is the owner's to set in Settings at any time; the plan works with any value. Recommended
before the canaries (§17, no longer a blocking question): a spending limit on the OpenRouter key itself.

### 4.5 `RunRequest.count` ≤ 100 and `MAX_COMPOSE_SCENES` = 100

The autopilot never sends a `RunRequest`; its limit is the set's: ≤ 100 scenes (`scenes.ts:13`), one set

### 4.7 The scene-review switch ON

- The launch click accepts W, which includes each avatar's compose **and** the draw of its planned
  `n_a` photos. Compose starts at once.
- The avatar then waits in `awaiting-review` (notification «Сцены ждут проверки: Mia»). The owner reviews
  on «Фото» exactly as today (CS.6); the strip shows the launch banner (S4.9b).
- The review screen's paid actions on a launch's set — ⟳ «Другая сцена» (a redraw) and a rewrite, and the
  resume of such a write — are **separate clicks** with their own estimate and cap
  (`sceneSets/estimate.ts:47-77`), allowed only while the avatar is `awaiting-review`. They are not drawn
  from the launch's allocation nor counted in its group, and the launch card shows them on their own
  line: «Правки сцен: $X (отдельно)».
- **Own scenes (M8, option б).** `continueAfterReview` never counts own scenes (`slot.kind: "own"`,
  category `"own"`, `sceneSets/toRun.ts:62-63`) in M and leaves them out of the frozen list: no video of
  the launch has the category `own`, so such a photo would have no place and would starve a planned
  video of its own category. To keep the owner from paying for scenes that will never be drawn,
  «+ Своя сцена» (both «По описанию» and «Как есть») is not offered on a launch's set, and the engine
  refuses an `idea` write or an own-text add there with `launch-set`. The line «свои сцены в запуск не
  войдут — K» stays as the defensive message for K > 0. Option (a) (own scenes fill singles first) was
  not taken: it needs an «own» category in the shape plan and breaks the exact per-category split.
- «Продолжить запуск: M фото» (on the strip and on the Autopilot card) calls
  `autopilot.continueAfterReview { launchId, avatarId, sceneSetId, revision }`:
  - `SCENES_CHANGED` if the revision moved (the existing code);
  - active scenes without text are removed by this click (the button says «K сцен без текста уберём»);
  - **M ≤ n_a** is required (A16): more active scenes than planned → `VALIDATION` with the reason
    `over-plan`, «сцен больше плана на K — уберите K»; adding scenes cannot raise the launch's spend;
  - M < n_a → fewer photos; the planner degrades that avatar's generated videos (§6.4);
  - then the launch approval of §3.4 and the slices. During `paused { restart }` (or `paused { owner }`)
    the click records the approval only; the paid draw waits for «Продолжить · до $R».
- **Refusals that close the bypass through «Фото» (M3).** While the launch is unfinished (the registry
  and the unlinked rule of §3.4), with `VALIDATION` reason `launch-set` («это часть запуска автопилота:
  управляйте им в «Автопилоте»»):
  - on a launch's set: `scenes.discard` («Пересоставить» included), `runs.startFromScenes`,
    `scenes.write { unwritten }` (the launch does its own «Дописать»), `scenes.cancel`, and an `idea` or
    own-text add (above);
  - on a launch's slice run: `runs.resume` and `runs.cancel` (S4.5b's soft stop ends a slice
    `cancelled` and resumable, so without this the Photos screen would offer to resume it);
  - `RunSummary` gains `launchId?` and `runs.list` marks such runs; the Photos screen shows «в запуске
    автопилота» instead of «Продолжить»/«Отменить».
- With the switch OFF the orchestrator does the same steps without waiting: text-less scenes are
  removed, the approval follows the compose.

The «Отрисовать» price the owner sees today for a set is replaced, for a launch's set, by the line
«в пределах запуска · до $Y» (Y = the avatar's draw allocation): no new money is accepted there.

### 4.8 What «Потрачено» means

Always the ledger (stage-2 money model): the launch's spent = Σ over its writer attempt ids
(`<sceneSetId>:writer-*`) and its slice runs' scope `{ runId }`: settled at cost, open reserves at worst.
The mockup's static «$0.96 из $2.20» becomes «Потрачено $S из $W′» (W′ the recomputed planned worst ≤
accepted), plus «Правки сцен $X (отдельно)» when there are any (`<setId>:write-*`). The same sum is the
launch group's committed in `Budget` (§4.10) and the S of «Продолжить · до $R», R = W′ − S.

### 4.9 A balance preflight

`/credits` today parses only `total_usage` (`money/reconcile.ts:41-43`). OpenRouter's `/credits` also
returns `total_credits`; reading it (lenient, optional) gives a balance. **Worth adding as a warning
only** (S4.5e): the plan screen says «На балансе OpenRouter $X — меньше предела запуска $W; при нехватке
запуск встанет на паузу» when X < W. Never a gate: the balance is account-wide (`reconcile.ts:11`) and
lags, and a 402 mid-launch is already a clean `paidHold { credits }`. One free GET per estimate, cached
60 s, skipped without a key. The same value can later fill the sidebar's «Баланс OpenRouter»
(`renderer/App.tsx:~181` says the contract has no data for it yet).

### 4.10 Who enforces which ceiling

**The launch group (M1, S4.2).** `BudgetLimits` gains an optional
`groupOf?(req: { attemptId, scope }) → { key, capMicros } | null`, next to today's cap callback
(`runCapMicros: (scope) => caps.get(scopeKey(scope)) ?? 0`, `engine.ts:964`). `tryReserve`
(`budget.ts:166-185`) and `tryHold` (`budget.ts:281-311`) add one check after the scope cap: when the
attempt belongs to a group, the group's committed (settled at cost, all time, + open at worst + held, over
every ledger line whose reserve maps to the same group key) + this worst ≤ the group's cap, else the
refusal `RUN_CAP_EXCEEDED` with the group's numbers (a `limit` for the run job, like a cap). `totals()`
already walks the whole ledger on every reserve (`budget.ts:469-488`); the group adds one predicate per
line. **The ledger format does not change** — r1 said it would, which was wrong: the group is derived
from attempt ids and scopes already on each `reserve` line. The engine's `groupOf` reads the launch
registry (§3.4): an attempt whose id starts with `<launchSetId>:writer-` (compose and the launch's own
«Дописать»), or whose scope is `{ runId }` of a launch slice, belongs to `launch:<launchId>` with cap W′.
Review writes (`<setId>:write-*`) do not. The group is registered before the launch's first reserve and
restored from the launch file at library open, before any paid command can run; a group whose launch is
finished maps nothing.

## 5. Photos

### 5.1 Which library photos

Per avatar, the **pool** = `eligibleUnusedPhotos(avatarId)` (`library.ts:897-905`: eligible by the one
rule `library/eligibility.ts:38`, not rejected, not used by a record, not reserved by a queued render or
a pending intent `library.ts:795-800`) ∩ `source.category ∈` the launch's categories (built-in ids
`shared/engine/categories.ts:12` and custom `cat-*` `:15,23`) − photos held by any saved montage draft
(new `photoIdsInDrafts`, S4.5c; drafts reserve nothing today, `montages/service.ts:17-18`, so without it
a manual render would hit `PHOTO_UNAVAILABLE`). Rules:

- usage must be `ok` (`AvatarUsage`, `state.ts:366-372`); `unknown` (index stale, unreadable log)
  blocks that avatar's library videos (fail closed — `eligibleUnusedCount` reads 0 then,
  `library.ts:909-911`);
- photos with an unknown or deleted category, own-scene photos (`"own"`) and imported photos are never
  taken from the library (they cannot match a chosen category, or are not run photos);
- photos past `photos.list`'s 500 cap (`commands.ts:97`, `photoRecords.ts:82-86`) are eligible, so the
  owner must be able to see them to reject them: prerequisite P2 (a cursor).

Generated photos of the launch are the launch's own and go to its generated videos of their category.
Own scenes never reach a launch's draw (§4.7, M8), so every generated photo has a planned category.

### 5.2 Mix → shapes

Per avatar, the shape counts are the mix applied to `videosPerAvatar` by largest remainder (ties to the
earlier shape: single, collage, slides): 10 videos → 7 / 2 / 1; 50 → 35 / 10 / 5; 3 → 2 / 1 / 0; 1 →
1 / 0 / 0. The mix is a per-launch control (default 70/20/10, integer percent, sum 100, remembered per
viewer in `localStorage`).

### 5.3 Library first, then generation

1. Slides first (they need the most same-category photos), then collages, then singles, by video key
   order. A library video is filled only from one category; sizes are drawn by seed: collage 2–4, slides
   5–7, falling back to the smallest size the category can fill.
2. **No near-duplicates** inside one video: every pair's PDQ distance > 20 (`hammingDistance`,
   `src/core/pdq/hamming.ts:1`; the threshold the run gate uses, `runs/config.ts:55`, `pdqClaims.ts:45`).
3. **Singles prefer verified faces**: photos with a stored `qa.faceCos` (the face gate ran,
   `runs/faceGate.ts:107-108`), highest first; photos without one (profile, back, gate skipped) go to
   collages and slides first. The sidecar has no pose (`library/schemas.ts:103-109`), so `faceCos` is the
   proxy.
4. A video the library cannot fill becomes **generated**. Generated sizes are fixed at 3 (collage) and 5
   (slides): variety from library photos is free, generated photos are paid, so the planner asks only for
   what the mockup and the owner's money facts count (1.8 photos per video at 70/20/10).
5. Each generated video gets a category: the chosen categories in a seeded order, round-robin over the
   generated videos (slides first). The per-category need is exact, and compose receives it as an
   explicit `split` (today the planner always uses `splitCount`'s even split, `planner.ts:207`,
   `categories.ts:138`; S4.5a makes the split an internal input), so «same category» holds without
   mixing.
6. «Сначала свободные фото из библиотеки» OFF → every video is generated. «Догенерировать недостающие»
   OFF → videos the library cannot fill are dropped at plan time (the plan shows «Видео: 7 из 10 — не
   хватает фото»). Both OFF → «Запустить» disabled.

### 5.4 Assignment of generated photos and collisions

- As each slice ends, its photos (`RunResult.photoIds`) are assigned to that avatar's generated videos
  of their category, in key order, under the same pdq and face rules; the assignment is written to the
  launch file before any render.
- A photo taken meanwhile by the owner (a manual render) → the autopilot's render answers
  `PHOTO_UNAVAILABLE` (free); the video takes another free photo of the same category from the launch's
  leftovers or the library pool; else it degrades. Exception (L1): after a restart, while a pending
  intent carrying this video's key exists, `PHOTO_UNAVAILABLE` means «wait for recovery», never re-pick.
- Leftover photos (more than needed after degrades) stay free in the library.

### 5.5 CS.8 angles

- A custom category with its own `poses` makes the planner draw each slot's angle from them (CS.8a,
  `planner.ts:164`), whatever the launch's toggles say.
- Built-in categories use the launch's «Ракурсы» toggles `{ profile, back }` (`RunPoses`,
  `state.ts:705`), default both OFF (front and three-quarter only). The scene set carries them as compose
  already does (`shared/engine/scenes.ts:225-231`).
- Profile and back photos skip the face gate, so they carry no `faceCos` and land in collages and slides
  by rule 5.3.3.

## 6. Montage

### 6.1 The spec generator

`autopilotSpec(video, photos, track, seed, options)` — pure (`shared/autopilot/spec.ts`), producing a
complete `MontageSpec` (`shared/engine/montage.ts`) with `focus: null` cells (filled in §8.2):

| Shape | Clips | Duration by seed (100 ms grid) | Motion |
|---|---|---|---|
| single | 1 photo clip | 6.0–10.0 s in 0.5 s steps | `kenburns` mostly, `pan` sometimes, by seed |
| collage 2–4 | 1 collage clip, `stagger: true` | 7.0–10.0 s in 0.5 s steps | `kenburns` |
| slides 5–7 | N photo clips | per clip 1.2–1.4 s by seed, total `clamp(N × per, 4000, 10000)` split by `splitEvenly` | per clip, by seed |

- **Hard cap**: Σ `durationMs` ≤ `AUTOPILOT_MAX_TOTAL_MS = 10 000`. Today `defaultSpec` makes 8 s for
  single and collage (`defaultSpec.ts:20,46-52`), but slides of 8+ photos exceed 10 s (8 × 1300 =
  10 400, `defaultSpec.ts:54-60`) and `MAX_TOTAL_MS` is 15 000 (`montage.ts:28`). The generator never
  calls `defaultSpec` for slides above 7 and builds its own durations; the engine's autopilot render path
  **refuses** (never clamps) a spec above 10 000 ms (A8). Manual montage keeps 4–15 s.
- Seed: `seed = fnv(planSeed, avatarId, videoKey)` → durations, motion choice, the spec's own `seed`
  field (pan direction and Ken Burns in/out via `motionPlan`, `motion.ts:78`). The track, its `startMs`
  and the sticker depend on the library's state, so they are chosen once at assignment and written into
  `videos[k]` (§3.3); the spec is then a pure function of the launch file, and a re-submit after a crash
  renders the same video.
- **No text layer** (decision 8). `options.captionSource` is `null`; when the owner defines the text
  source later, a non-null source adds one text layer through the exported caption validator (stage-3
  invariant 19) — no other change to the generator.
- **Stickers**: OFF by default (the mockup). ON → one built-in sticker layer for the whole video
  (`STICKER_MANIFEST`, 10 stickers, `shared/stickers/manifest.ts:50`), chosen by seed while avoiding the
  sticker of the avatar's previous autopilot video, size 0.18–0.24, centred on one of four anchors kept
  clear of the Reels UI zones (top-left, top-right, mid-left, mid-right). Own stickers never.

### 6.2 Photo need and price per shape

For the plan screen (decision 3 «price per shape visible»): «Одно фото ≈ $0.07 · Коллаж ≈ $0.21 ·
Слайды ≈ $0.35» = 1 / 3 / 5 × `photoExpected` (≈ $0.07, the engine's expected, §4.2; estimates at
today's prices; the engine returns them from the unit prices).

### 6.3 Variety

Variety comes from: shape sizes on library photos, durations, motion, the spec seed, the music start
(§7), the sticker. No uniquifier copies (dropped 2026-09-29); one photo → at most one video (A7).

### 6.4 Degrade rules (fewer photos than planned)

Deterministic, per avatar and category, applied after the last slice (or after review removals):
slides 5 → collage 4 if 4 photos; collage 3 → collage 2; a single without a photo is dropped; then
drop videos from the highest key down until the rest are fillable. Every degrade or drop is logged with
its reason («2 видео меньше: 3 фото не получились»).

## 7. Music

- **Candidates**: every stored trending track — `inList` true or false, since `hasTrack`/`openForRender`
  serve both (`trackStore.ts:314,331`) while `list()` offers only `inList` (`:304-311`) — whose
  `explicit` is false (`trackRecord.ts:49`; the engine filters nothing today, `musicOps.ts:223` is
  renderer-only), plus own audio media the owner flagged «для автопилота». Accepted consciously: a
  track whose list entry lacks `is_explicit` is stored as not explicit (`explicit = is_explicit === true`,
  `music/listSchema.ts:258`), so «never explicit» trusts the provider's flag; a three-state flag is in
  the backlog.
- **Own-track flag** (data model): media records are write-once (`mediaRecords.ts:13`), so the flag is
  an append-only `<library>/media/autopilot-tracks.jsonl` `{ mediaId, on, at }`, last line wins (the
  `rejected.jsonl` pattern, `library/eligibility.ts:43`). A torn or unreadable log reads as «no own track
  flagged» (fail closed: the autopilot uses fewer tracks, never an unflagged one). Command
  `media.setForAutopilot { mediaId, on }`; `MediaSummary.forAutopilot?: boolean` (optional, so the
  strict schema stays additive). Only valid own tracks (`kind: audio`, m4a, a duration,
  `videos/ownTrack.ts:42`) can be flagged.
- **Least-used per avatar**: usage = the avatar's video records whose resolved `spec.music` names the
  track (`trackId` for trending, `mediaId` for own; the record keeps the resolved spec,
  `record.ts:73,97`) + the videos of this launch already given that track. Ties: not among the avatar's
  last 5 videos → `inList` (current trends) first → own → seeded order. No helper exists today
  (S4.4 adds `trackUsage(avatarId)` over the records; S4.5c pins that `spec.music` survives in the record).
- **Length**: `startMs` = the first highlight (not `likelyDefault`) with `startMs + total ≤ decodedMs`;
  else 1500 (`LIKELY_DEFAULT_MS`, `shared/music/trackShape.ts:7`) if it fits; else 0 if it fits; else the
  track is unfit for this video. The engine's own check stays (`track-too-short`,
  `shared/montage/trackIssues.ts:17-45`).
- **Auto refresh of trends** (stage 3 left it to Stage 4, stage-3 plan «Stage 4 hooks»): a refresh may
  leave without a click only when **all** hold: a music key is stored; no refresh is running; the
  current list is older than 72 h or there are fewer than 10 candidate tracks; automatic sends in the
  rolling 31 days ≤ 9; total sends in the window ≤ 19 (so ≥ 10 of 30 stay for manual use); the server's
  `remaining`, when known, ≥ 11; this launch has not refreshed yet; no automatic refresh in the last 72 h.
  One attempt, never retried (stage-3 invariant 30's rules otherwise unchanged). The quota ledger's
  lines stay exactly as they are (`send` is a `strictObject`, `music/quotaLedger.ts:80`: a new field would
  read as damage to an older build and close refreshes for 31 days, `:24-30`); instead the auto refresh
  first appends its send id to a separate `userData/music/auto-sends.jsonl` `{ id, at }` (fsynced), then
  goes through the normal quota reserve. The auto count = lines of that file in the rolling 31 days; a
  torn or unreadable file counts as 10 (fail closed: no automatic refresh). Triggered only by a launch:
  at start, and when a launch has `waiting-music` videos — at most once per launch. The plan screen says
  «Обновим тренды при запуске (осталось 21 из 30)». Stage-3's rule «only a user click sends a request»
  is amended to «a click, or a launch within the auto rule».
- **No fitting track → the video waits**: it becomes `waiting-music`; its photos are not reserved (the
  owner may use them; then it re-assigns or degrades). The launch stays `running` (idle) while only such
  videos remain; a new candidate (a finished refresh, a flagged own track) resumes them automatically
  (free); «Стоп» drops them. The plan screen warns before start: «Подходящей музыки нет — видео будут
  ждать. Обновите тренды или отметьте свои треки «для автопилота»». Never a silent render (A9).
- The mockup's chip «Jamendo · по категории» is stale (Jamendo is gone, no code matches; flashapi has no
  genre tags). It becomes «Тренды + мои · N треков» with the auto-refresh line.

## 8. Renders and records

### 8.1 Submitting renders

- Through the video service's internal `render(source)` with `{ montageId: null, spec, provenance }`
  (`videos/service.ts:296-316`); the contract command `videos.render` is unchanged.
- The autopilot keeps **≤ 8 unfinished renders** (queued + running) of the 20 the queue allows
  (`MAX_UNFINISHED_RENDERS`, `queue.ts:70`); the owner always has ≥ 12 (A10). `RENDER_QUEUE_FULL` →
  wait for a render's end event.
- Before submitting, the engine re-runs `export.check` once per launch start and the free-space check
  per render (`exportRoot.ts:299-301`, 2 × `estimateBytesUpper`; ≈ 4.5 MB per 10 s video,
  `shared/montage/estimate.ts:26`). The plan screen shows «Диск: нужно ≈ X МБ».

### 8.2 Focus

A headless spec's `focus: null` is filled inside the render command's 25 s deadline
(`videos/service.ts:154-156,507`; `FOCUS_FILL_BUDGET_MS = 60 000`, `focus/focusResolver.ts:51`); on a
miss it falls back to a stand-in (`focusResolver.ts:188`). The face worker is one FIFO lane shared with
the runs' face checks (`face/worker/workerGate.ts:26,126-166`). Under a launch both are busy, so:

- the orchestrator **prefetches focus** (`focusFor` per photo, cached in `focus.json`) as a separate
  free step before submit, with no 25 s deadline (its own per-photo timeout); the submitted spec then
  carries filled focus and the render never touches the face lane;
- P3 gives run face checks priority over detects, so prefetch waits behind paid work, never the reverse.

### 8.3 The record

- `VideoRecord` gains optional `origin: "autopilot"` (absent = manual), `launchId`, `launchVideoKey`;
  so do the pending intent and `VideoSummary` (`origin?`, `launchId?`).
- **No `VIDEO_RECORD_SCHEMA_VERSION` bump (D5).** The record schema is loose and an older build ignores
  extra fields by design (`record.ts:45-50`); a bump would make every older build read the whole
  library's usage as `too-new` (`videoRecords.ts:133`) for fields it has no use for. Precedent: the
  sidecar stayed v1 with new optional fields while Studio is unreleased (stage-2 plan, T6c). If Studio
  is released before Stage 4 lands, the same reasoning still holds (fields are optional and only
  informative); a bump becomes necessary only for a field an older build must not ignore.
- The engine refuses an autopilot-provenance spec above 10 000 ms or with a text layer (A8, A9).

### 8.4 «Опубликовано»

- Records are write-once (the commit is `link(intent, record)`, stage-3 invariant 23), so the mark lives
  in an append-only `avatars/<avatarId>/published.jsonl` `{ videoId, published, at }`, last line wins,
  next to `rejected.jsonl`. Unreadable → marks unknown, shown as unmarked with a notice; nothing depends on
  it (decision 4).
- Command `videos.setPublished { videoId, published: boolean }` → `{ video: VideoSummary }`;
  `VideoSummary.publishedAt?: string | null`; `video.changed` emitted.
- UI: a toggle «Опубликовано» on the autopilot results list and on the video tiles of «Фото» (the
  videos column), a filter «Скрыть опубликованные». Studio never deletes on it.

### 8.5 «Удалить видео и отклонить фото»

`videos.delete { videoId, mode, rejectPhotos?: true }` (`commands.ts:431`, `videos/delete.ts`).
Order: (1) the export folder must answer, as today; (2) append a reject for every scene photo of the
record to `rejected.jsonl` (`library.setRejected`, `library.ts:1029`); (3) delete as today
(`delete.ts:185,208`). A crash between 2 and 3 leaves the video with rejected photos (harmless; delete
again); the reverse order could leave free, unrejected photos for the next launch to take. Result adds
`rejectedPhotoIds`. Available on every video, autopilot or not.

**Deleting a published video (M9).** A plain `videos.delete` removes the record, and its photos become
free again (`library.ts:1013-1015`); `published.jsonl` keeps only the video id. So «опубликовал →
удалил в Studio» would let the next launch build a new video from photos already posted. Default,
**pending owner** (Q4): for a video marked «Опубликовано» the delete dialog preselects «Удалить видео и
отклонить фото» (the plain delete stays one click away); for other videos the plain delete stays the
default. Alternative kept in reserve: `published.jsonl` lines also carry the video's `photoIds`, and the
autopilot's pool (§5.1) excludes every photo ever published, even after its video is deleted — no
dialog change, but a second exclusion source to keep consistent.

  `Budget` launch group on every reserve and hold (a reserve that would lift the group's committed above
  W′ is refused), and checked again by the orchestrator. Tests: the group in `Budget` alone (S4.2:
  boundary at W′ − 1 / W′ / W′ + 1 µ$, holds counted, a review write `<setId>:write-*` outside the group,
  restoration after a restart before the first reserve); a property test over random prices (rising,
  falling), slice sizes, room, «Дописать» after a stop, and crash points.
- **A3. Nothing is raised.** No autopilot path raises a cap or the monthly budget; a resume never
  re-plans; a price rise shrinks a slice or holds.
- **A4. Ids before calls.** `launchId`, every `sceneSetId`, the set's run id and every slice run id are
  on disk before the call that uses them. A kill at every boundary of §3.6 → after «Продолжить» no second
  set or run exists for any step, the ledger never sees `ATTEMPT_ID_REUSED`, and videos = plan − dropped.
- **A5. Restart.** After an engine or app restart a launch makes no reserve, submits no render and sends
  no music request until «Продолжить · до $R» is accepted (`autopilot.resume` with
  `acceptedRemainingMicros ≥ R′`).
- **A6. The buttons create no open reserves.** «Пауза» and «Стоп» abort nothing: after the click no new
  chunk and no new attempt starts, in a slice run or in a scene job, and every attempt already in flight
  ends under the ordinary rules. (An attempt in flight may still time out or lose the network and leave an
  open reserve by those rules; the buttons never cause one.)
- **A7. Photos.** No photo is in two videos. No photo is used that is rejected, used, reserved, held by a
  saved draft, of another avatar or (from the library) outside the chosen categories. Property test.
- **A8. ≤ 10 s.** Every autopilot spec's total is ≤ 10 000 ms; the engine refuses one above, never
  clamps.
- **A9. Spec content.** No text layer; music always present (never silent), never explicit, track
  ≥ `startMs + total`; stickers only when the launch enables them, built-in only; no own media.
- **A10. Queue share.** ≤ 8 unfinished autopilot renders at any time; the owner's renders are never
  refused because of the autopilot while it holds ≤ 8.
- **A11. Music quota.** Automatic refreshes ≤ 10 in any rolling 31 days; never one that leaves fewer than
  10 of 30; never two at once; never retried; never without a key. Boundary tests at 9/10 auto and 19/20
  total.
- **A12. One launch.** At most one non-terminal launch per library; a library switch is refused while a
  launch is `running`.
- **A13. Holds vs pause.** Free work continues during a `paidHold`; nothing continues during `paused`.
- **A14. Spent from the ledger.** A launch's spent = the ledger over its own attempt ids and scopes
  (settled + open at worst); review writes are reported apart and never counted against W.
- **A15. Provenance and marks.** Every autopilot record carries `origin`, `launchId`, `launchVideoKey`;
  manual records carry none; the published mark never rewrites a record; «Удалить видео и отклонить фото»
  rejects before it deletes.
- **A16. Review bounds and no bypass.** With review ON an avatar's draw ≤ its planned count, own scenes
  never counted or drawn; review-screen paid writes (redraw, rewrite) are their own clicks and never in
  the launch's group or allocation; while the launch is unfinished, its sets refuse discard, manual
  approval, manual «Дописать», cancel and own-scene adds, and its slice runs refuse manual resume and
  cancel — so nothing paid of the launch moves while it is paused.
- **A17. ≤ 100 per avatar.** A plan that needs more than 100 generated photos for one avatar is refused at
  estimate and at start.
- **A18. One estimate.** The preview and the start use the same `planLaunch`/`launchEstimate`; for one
  avatar and n in 1..100 the launch's worst and expected equal `composeEstimate(n) +
  runEstimateFromScenes(n)` on the same price book.
- **A19. One admission rule.** The manual «Продолжить» and every automatic continue admit paid work by the
  same test: `Budget.blocked()` is null and the launch's own hold cause is gone. An open reserve of this
  session alone never blocks either, and never unblocks a hold that requires «Сверка» (`network` with `nextAt: null`; a network hold with a retry still to come is the wait of an automatic continue, which «Продолжить» may skip under the same ledger test, §23).
- **A20. Stop leaves no locked avatar.** After «Стоп» in any set phase (composing, awaiting review,
  approved without a slice, drawn in part), and after a launch file is removed as unreadable, no set or
  run carries a `launchId` that blocks anything: every refusal of A16 treats a `launchId` that does not
  name a readable unfinished launch as absent, and the owner can compose, draw, discard or resume as for
  any manual set or run. Tests in S4.5a (per phase) and S4.6d (with a kill during the unlink).
- **A21. Room counts live caps.** The month room used for `monthFit` and slice sizes subtracts the
  unspent cap of every live scope; a slice sized to that room never meets `BUDGET_EXCEEDED` mid-run from
  a job that was already running when it was sized (test with a concurrent manual run).

Stage-2 invariant 4 gets the clarification of §4.1; stage-3's quota rule gets the amendment of §7. Both
texts are updated in their docs by the tasks that implement them.

## 21. S4.6b1 as built (the paid path, 2026-10-09)

- **One hold, one timer, decided in the write (fix round 1).** The steps share the launch's single hold. `ctx.raisePaidHold(hold)` is a compare-and-set INSIDE the store's write on the fresh file: it stands when none stood or when it outranks what stood, which it displaces. Ranks (`holdRank`): 0 a waiting hold (a retry still to come); 1 credits, key, price, budget, a price list that stayed unavailable; 2 a network hold with `nextAt: null` (it displaces every hold of rank 1, so a third drop is never hidden behind a 402 that «Продолжить» would clear at once, A19); 3 halt and internal (nothing displaces them). Among equals the first stays. `ctx.clearPaidHold(expected)` clears only that very hold. The retry timer is created before the hold is written, bound to the hold that WON (an in-memory arm, not the time stamp), replaces the timer of what it displaced, and is taken back when its hold lost or was displaced. Every drop is counted in its own job (`autoContinues`) whatever hold stands; a drop uses one of the job's two continues only when a wait can serve it (not while a hold for a person stands), and the third drop is decided by the drop's NUMBER, not by the continues left: a third drop landing under another job's wait or hold becomes the network hold with no retry (the rank puts it above the others, except halt and internal).
- **The table.** A job's error code picks the row (`causeOf`): credits, key, halt (`SETTLE_ABOVE_WORST`, `LEDGER_WRITE_FAILED`) → `paidHold` for a person; no answer / final 429 / 5xx / timeout → the bounded continue; `PRICE_UNAVAILABLE` → retry at 5 / 15 / 60 min, then `price-unavailable` with `nextAt: null`; `BUDGET_EXCEEDED` mid-slice → `budget` (`resume-slice`, `Engine.resumeSliceHold`) and the log line `budget-ended`; at a compose / «Дописать» start → `budget` (`new-slice`, the step's worst case); `RUN_CAP_EXCEEDED` → the slice is finished, no hold; `PRICE_CHANGED` at a started slice → `price { slice, toPhotos: 0 }`; `IN_FLIGHT` → wait; `MASTER_FACE_UNUSABLE` / `FACE_GATE_UNAVAILABLE` / `DESCRIPTOR_INVALID` → `skipped`. Scene jobs: why a compose / «Дописать» stopped is read from `set.write.stoppedBy / stoppedError`; a set's compose and the «Дописать» that continues it are ONE job for the counters (`<setId>:scenes`). The first cause holds; a second failure only parks its avatar. Free work goes on (asserted per row).
- **Bounded continue (Q2 = A, the plan default).** Per job, in the launch file: `autoContinues[jobKey] = { drops, continues ≤ 2 }` (key = slice run id or `<setId>:scenes`); `priceRetries ≤ 3` launch-wide. Drops 1 and 2 → `paidHold { network, drops, attempt, nextAt }` and a timer at +1 / +5 min; drop 3 → `nextAt: null`. The timer is armed BEFORE its hold is written, checks `ctx.isRunning()`, that the hold is still its own, and `port.admitted()` (`Budget.blocked()` null; A19) and then clears the hold and restarts the passes. Pause, stop, quit, suspend, a `begin` and a release cancel it. Q2 = Б is `networkWaitsMs: []` (the first drop holds); the default stays until the owner answers (the steps are still not the engine's default; a later task wires them).
- **Admission.** A `network` hold with `nextAt !== null` is the wait of a continue, so «Продолжить» admits it (the ledger test still applies); a hold with `nextAt: null` still needs the launch's open reserves settled. `RECONCILE_REQUIRED` met mid-run becomes `network { nextAt: null }` and counts one drop of its job (the contract has no hold of its own for it; the exit is the same).
- **Failure-rate guard.** `Engine.sliceOutcome(runId)` (journal + ledger) counts slots closed by `QA_REJECTED` / `MODERATION_REFUSED`. Before another slice is drawn the previous one is judged: slots ≥ 4 and failed × 2 ≥ slots → `skipped { failure-rate, failed, total }`. Not applied to an avatar's last slice (nothing left to protect; the photos that came are kept). Read before the next draw rather than at the slice's end, so a pause cannot lose it.
- **`host.power`.** `Orchestrator.power("suspend")` is synchronous: nothing counts as running (`ctx.isRunning`, `mayPay`), the steps soft-stop what is in flight and cancel their timers. `"resume"` (a launch that ran): the paid part does NOT claim a network check (the price list comes from a cache and a dated book, so reading it proves nothing, and a probe of its own would be a request outside the launch's accounting; a network still down shows as the next drop of a job, on the bounded continues). `wake` puts right what the sleep interrupted: a waiting hold whose timer was cancelled is armed again for the remainder, one that came due goes through the timer's own check (`#fire`: admission rule, hold identity), a launch with no hold starts its passes again; the free part is begun again. The owner's «Продолжить» (also on a launch that runs with no hold) or a new start clears the sleep flag, so a lost `resume` cannot strand a launch.
- **Composer.** The finish retry is armed only while the launch runs, fires only while it runs, and is cancelled by `begin`, `drain`, `release`, `complete`; a vote while the launch does not run reaches no finish. `suspend` / `wake` are forwarded.
- **Soft stop.** Pause / Stop / sleep also cancel the busy-avatar wait (it was an unref'd timer a drain waited on; now clearable and woken by the drain).
