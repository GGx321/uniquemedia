# Studio — Stage 2 plan: avatars and photos

Goal: in the Studio app, create an AI avatar and generate a series of scene photos
of it — 20 photos in one run, with the expected and the worst-case cost shown
before anything is spent.

Inputs: the product concept (Claude Doc "Studio — концепция продукта"), the Stage 0
spike (`spike/studio-api/README.md`, results 2026-09-24), the Stage 1 skeleton
(`studio/`), the Stage 1 whole-slice review, and the critic review of this plan
(revision 2).

Stage 2 ships as three slices, each releasable on its own:

- **2a — engine and avatar**: engine process, API contract, money, OpenRouter client,
  library, age gate, avatar creation, Settings.
- **2b — photo run**: scene system, job queue with cancel and resume, PDQ gate,
  the Photos screen.
- **2c — face gate**: face similarity in the engine, retries on face mismatch.

## Money model

Ledger lines (append-only JSONL, integer micro-dollars, `fsync` after each append):

- `reserve { attemptId, jobId, runId | avatarId, model, worstMicros, at }` — written **before** the request is sent.
- `settle { attemptId, costMicros, estimated, at }` — written after the final response of the attempt: a 2xx → its `usage.cost` (worst case with `estimated: true` if the field is missing); any final non-2xx (refusal, 4xx, 5xx after transport retries) → `costMicros: 0` (OpenRouter image billing is all-or-nothing and failed generations are not billed).
- `release { attemptId, reason, at }` — only when the request provably never reached OpenRouter (failed before `fetch`).

Rules:

- Transport retries after a non-2xx (429/5xx with `Retry-After`) stay inside one attempt id. Within a job, a new attempt id is taken from the slot's pre-allocated list only after a 2xx (e.g. a QA rejection), an abort, a timeout, or a moderation refusal (the fallback); a final non-2xx that got no answer (429, 5xx, the network) stops the run, and its resume takes the slot's next id — one of its spares, since a free attempt never counts toward its paid ones (T6).
- An unsettled `reserve` counts at its worst case — in the run cap, in the global budget, and toward the slot's attempt limit — until reconciled.
- Reconcile (a user action; after a restart the app shows what needs reconciling but spends nothing): wait at least 2 minutes after the last request (`/credits` lags), compare the `/credits` usage delta since the last reconcile with the ledger total for the same window and show both, then close every open `reserve` with `settle` at its worst case and `estimated: true`, and move a torn last line to `ledger.torn`.
- A truncated last JSONL line stops all paid calls until the user reconciles.
- Two limits, checked atomically by one `Budget`: the run cap (default, image age check off — the app's own default: 20 photos × 3 attempts × $0.05 image + the writer's worst, ceil(count/25) chunks × 2 attempts × $0.0375 (T5c round 2: raised from $0.035, `WriterCall.inputTokens` 12K → 14K) ≈ $3.075; with the toggle on, 20 × 3 × ($0.05 image + $0.00525 age check) + $0.075 writer ≈ $3.39; at the contract's maximum of 100 photos (4 chunks) ≈ $15.30 off / ≈ $16.875 on; money/estimate.ts's `WriterCall.slotsPerCall`/`.maxAttempts` and `writerWorstMicros` are the one source of truth for the writer's share; avatar jobs are capped per command at their own worst case: the descriptor ≤ $0.0275, a batch of 4 candidates $0.16 off / $0.181 on, a whole new avatar $0.1875 off / $0.2085 on, rewriting a descriptor (`avatars.rewriteDescriptor`) the same ≤ $0.0275 as the descriptor alone, unaffected by the toggle since it never touches candidates or age checks; importing an existing avatar (T6c, `avatars.importAvatar`) ≤ $0.03775 — one mandatory one-time image age check ($0.00525 worst) plus up to 2 vision describe attempts ($0.01625 worst each), unaffected by the toggle since its own age check runs either way) and the global budget from Settings, counted per calendar month (UTC), default $10.
- Estimates show both expected and worst case.
- Prices come from `/api/v1/images/models/<id>/endpoints` and `/api/v1/models` (chat); a dated fallback table is used only when the fetch fails, and the UI says so.

## Invariants (tests must pin each)

1. No test can spend money: the OpenRouter client takes the key and the base URL as parameters and refuses to run without a key; tests never pass a real key; `studio/engine` and `studio/node` never read `process.env` or use `Bun.*` — a static test checks every module reachable from the engine entry (main may read `ELECTRON_RENDERER_URL` in dev only).
2. Money is integer micro-dollars; the ledger is append-only; a `reserve` is on disk before its request leaves.
3. Before any paid call: spent + unsettled reserves + in-flight worst case + this attempt's worst case ≤ the run cap and ≤ the global budget.
4. Abort, timeout or crash cost the worst case until reconciled; after a restart nothing is spent without a user click.
5. An attempt id that got a 2xx, an abort or a timeout is never sent again; only transport retries of a non-2xx (429/5xx) repeat inside the same attempt id. Every new attempt takes the next id from the slot's pre-allocated list.
6. Plan order: slots with pre-allocated attempt ids (`slot#1..#5`: at most 3 of them paid, the rest spares for attempts that got no answer) are written before the writer's calls (one per chunk); prompts are written before the first image call; resume uses the plan and never re-plans.
7. At most 3 paid attempts per slot across all QA branches and fallbacks. A paid attempt is one that was, or may have been, billed (`attemptPaid`, runs/journal.ts): a 2xx billed above zero, an open reserve (abort, timeout, network), or a reconcile's estimated settle. A free one — a final non-2xx settled at zero, a request released unsent, or a 2xx billed at zero (a $0 model) — uses a spare id instead.
8. Every avatar is 21+ in its descriptor schema and every prompt — always enforced, whatever the toggle below. The paid image age check is optional and off by default (owner's decision, 2026-09-27): when on, every photo passes it before it enters the library; when off, a photo enters right after its image checks, with no `qa.age` verdict, and the owner's own pick is the gate.
9. Reference images come only from the avatar's own library frames: generated, or the owner's import (T6c) — no other user file can become a face reference.
10. The API key lives only in `safeStorage` (main) and the engine's memory; never in the renderer, logs, library files, or child-process environments (engine and ffmpeg are spawned with an explicit env without `OPENROUTER_*`).
11. Library write order: image file written and `fsync`ed first, sidecar JSON second (the sidecar is the commit, also written temp + `fsync` + rename); on start, files without a sidecar go to `quarantine/`.
12. `studio-media://` serves only by id (`studio-media://photo/<avatarId>/<photoId>`): main validates both ids against `^[a-z0-9-]{8,64}$`, builds the path by the library's naming convention (`avatars/<avatarId>/photos/<photoId>.<ext>`, extension from a fixed image allowlist), checks with `realpath` that it lies inside the library root, and serves only image MIME types; registered as privileged without `bypassCSP`.
13. The base-URL override used by end-to-end tests is compiled out of packaged builds.

The canary needs the owner's explicit approval, costs about $0.1875 worst case with the image age check off (the app's own default: the descriptor + 4 candidates, invariant 3's avatar-job cap) or $0.2085 with it switched on (the descriptor + 4 candidates + their age checks), and runs in the real app — never from a test or an agent.

1a. Only if you plan to run this canary with the image age check switched on: if you also plan to run `ageGateRunner.ts` today, do it now, before step 2, or with a separate key; never between steps 2 and 5: its spend is outside the ledger and would show up as a false mismatch at step 5. With the toggle off (the default), this step does not apply — there is no age check to calibrate.
2. Run a baseline `money.reconcile` before the first spend (free: `GET /credits`), so the reconcile in step 5 has a real baseline to compare against instead of landing in reconcileLedger's "no baseline" branch (studio/engine/money/reconcile.ts).
3. Create one avatar: the descriptor call, then 4 candidate portraits.
4. Optional: cancel one extra batch mid-flight, to learn whether OpenRouter bills the cut-off requests (see "Open questions" below).
5. Wait out the quiet period (`RECONCILE_QUIET_MS`, 2 minutes) and reconcile; pass if the `/credits` delta ≤ the ledger total.
6. Write the numbers down in this doc (expected vs. worst, the `/credits` delta, the ledger total).

#### T6 — decisions

Code: `studio/engine/runs/` (pools, plan, journal, failures, writerPhase, qa,
remaining, runJob) and the `runs.*` commands in `engine.ts`.

- **Persistence.** A run lives in its library folder: `runs/<runId>/plan.json`
  (written once, atomically, before the writer's first call: the planner's
  slots, every slot's ids `${runId}:slot-N#1..5`, every writer chunk's ids
  `${runId}:writer-${chunk}#1..4`, the models, the age-check mode, the cap and
  the worst case estimated at plan time) and `journal.jsonl` (append-only,
  fsynced: writer chunks, prompts, every attempt's outcome, every slot's end,
  every job's start and end). A job — a start or a resume — folds the plan,
  the journal, the ledger's reserves and the committed photos: an id with a
  reserve is never sent again (invariant 5), a photo whose sidecar names one of
  a slot's ids ends that slot, and a lost last attempt settled at zero on the
  primary is read as a possible refusal (the prompt never goes back to the
  primary). An attempt released unsent never decides the route, and a
  fallback that never reached Seedream (released, or stopped between
  transport retries) is not used up. Prompts are re-assembled from the
  journal's writer sentences on every job, never trusted from the journal as
  they are.
- **When a run stops.** A new id only after a 2xx, an abort or a timeout (the
  money model): a timeout takes the slot's next id; a final 429, a 5xx after
  the transport retries or a network error stops the whole run from sending,
  its slots left open for a resume; a 401/402, a ledger halt, a reconcile
  needed, a non-moderation 4xx or a request that cannot be built stop it as
  fatal; the run's cap or the month stops only the slot that asked. Images
  already paid for when it stops still go through free gates into the library,
  after a user's cancel too (then under a short timeout of their own, not the
  cancel); such an image is dropped only when a gate is paid or broken. Every
  request asks `beforeSend` right before it leaves, so nothing is sent after a
  stop. Slots and writer chunks count *paid* attempts from the ledger (3 per
  slot, 2 answers per chunk: an open reserve counts), and two spare ids each
  keep attempts that got no answer from closing them. A chunk that can never
  be written (its answers used, or its prompt refused by moderation) ends
  every open slot, so the run is not offered for a resume that cannot help.
- **Pools.** One network pool for every run of the engine (the settings'
  concurrency): a 429 shrinks it by one at most once per 5 s; it grows back by
  one per streak of successes as long as its limit (1 → 6 in 16). A CPU pool
  (cores − 1, 1..4) runs the free QA gates; a paid gate runs in a network slot.
  A gate's slot is freed the moment its signal aborts, even if the gate itself
  ignores the abort. `runs.list` reads every run and loads prices once per
  model set, all at once.
- **Money.** The cap is the accepted worst case of `estimateRun` (PRICE_CHANGED
  with `>`), kept in plan.json for the run's whole life; the Budget checks every
  reserve against it and the month atomically. A resume is accepted like a
  start (`runs.estimateResume` → `runs.resume` with `acceptedWorstMicros`): the
  remaining worst case at today's prices, never above what the cap leaves;
  the cap is never raised.
- **QA gates** (`runs/qa.ts`): pass (qa fields into the sidecar), retry (the
  slot's next id, counts toward its 3) or reject (the slot ends); a slot that
  ends through its gates ends with QA_REJECTED. A gate is bounded by the run's
  cancel and its own timeout; a gate that throws or times out stops the run.
  With the image age check on, a run is refused with AGE_GATE_UNAVAILABLE
  until a gate named `age` is registered (invariant 8).
- **Contract.** `JobState` (run) and `RunResult` carry `avatarId`; new commands
  `runs.estimateResume` and `runs.list` (`RunSummary`, newest first, at most
  100); `runs.resume` takes `acceptedWorstMicros`; `RunRequest` takes
  `poses: { profile, back }` (T5c: profile and back only when the run allows
  them), passed to the planner and kept in plan.json; new error codes
  QA_REJECTED and AGE_GATE_UNAVAILABLE.
- **One writer loop.** `runs/writerPhase.ts`'s `runWriterPhase` is the scene
  writer's only chunk loop (T5b's `runWriterJob` is gone: it had no caller, and
  its tests now run against the phase, `runs/writerPhase.rules.test.ts`). A
  paid answer without content gets `emptyAnswerRefusal()` from
  `scenes/writer.ts`.

- **Architecture (round 2, closes most of round 1's findings).** Round 1 had
  both gates wired into `EngineDeps.qaGates` once, in `main.ts`, before any
  run — or any API key — exists; the age gate reached a client through a
  late-bound reference to the engine (`Engine.gateChat`, now removed) and
  the pdq gate took a `knownHashesFor` dependency with no real library to
  read. Round 2 gives both gates the RUN's own resources through `QaInput`
  itself instead: `chat` (the same client `runSlot`'s own image attempts use
  — built in `engine.ts`'s `#runPhotos` from `run.key` and
  `reportingTo(this.#networkPool, this.#deps.fetch)`, so a 429 from the age
  check shrinks the same pool a 429 from an image call would, and a key
  rotation mid-run never mixes two keys in one run), `beforeSend` (mirrors
  `AttemptParams.beforeSend`, T6 review L1) and `photosByAvatar` (the run's
  own `RunLibrary`, read fresh — never a dependency that has no library to
  fail open from). `main.ts` now just builds `createPdqGate()` and
  `createAgeGate()` with no arguments and no reference to the engine at all.
- **A paid gate's own queue wait must not count against its timeout.**
  Round 1's `checkOne` started the gate's own `timeoutMs` before asking the
  network pool for a slot, so the FIFO wait behind other slots' image
  attempts ate into it — a busy run (many slots, a small network
  concurrency) could time out an age check that, once actually running,
  would have answered in milliseconds, and every resume repeated the same
  spurious timeout. `runJob.ts`'s `checkPaid` now starts the timeout only
  once a slot is actually granted; the wait itself is bounded only by the
  job's own cancel. The wait also asks for priority over brand new image
  attempts (`pools.ts`'s new `{ priority: true }` acquire option, its own
  queue serviced before the plain one, tested in `pools.test.ts` without
  touching T6's own FIFO tests): an age check is work already paid for, so
  it should not be starved behind a stream of new generations, which also
  shrinks the window described next.
- **No paid request once the run has already stopped sending.** `checkPaid`
  re-checks `sending(ctx)` the moment its network slot is granted, before
  the gate's own request can leave — closing a race where another slot's
  failure stops the run while this gate was still queued. The age gate also
  forwards `beforeSend` into its own chat call (T6 review L1): if the run
  stops sending in the narrower window between that re-check and the actual
  HTTP try, the client's own transport ends the attempt as `aborted` without
  sending, and the gate reads that (with `input.signal` itself never
  aborted) as "already stopped", not as doubt about the photo.
- **A paid gate's own failure, classified like an image's.** Round 1's age
  gate turned every failure — including a rate limit, a network error, an
  invalid key, its own reserve refused — into a `reject` verdict, spending
  nothing more on this one photo but leaving every OTHER slot to hit the
  identical unresolved problem and get rejected one paid image at a time,
  instead of the run stopping the way an image attempt's own failure already
  does (T6 H1). `qa.ts` gained `GateFailure` (`{ error: EngineError }`,
  mirroring `engine.ts`'s own `EngineFailure`): the age gate throws one for
  everything classified as more than doubt about this photo
  (`runs/failures.ts`'s `classifyFailure`, reused as-is — TIMEOUT included,
  a deliberate decision, consistent with T6 H1: the run stops and the slot
  stays open for a resume). `reject` is now reserved for a moderation
  refusal, an empty/unreadable answer, or a clear no from `readAgeAnswer`.
  `runJob.ts`'s `keepImage` reads a caught `GateFailure`'s own T0 code:
  `BUDGET_EXCEEDED`/`RUN_CAP_EXCEEDED` are a *limit* (mirrors `ctx.limited`
  for an image's own reserve refusal — only this slot stops, others may
  still have room); anything else stops the whole run with its exact code
  preserved, so `AUTH_INVALID` still marks the stored key rejected and
  `INSUFFICIENT_CREDITS`/a ledger halt still reach the UI, never collapsed
  to a bare `INTERNAL`. A bill above the reserved worst case keeps the
  verdict (the image is paid for and passed, T6 M1) instead of throwing it
  away: `checkPaid` notices the now-halted ledger (`Budget.status().haltCause`,
  `haltIfLedgerHalted`) synchronously right after a paid gate returns —
  re-review finding L1 moved this out of `runGates` itself, which ran only
  after `checkPaid` had already returned and freed the network slot, leaving
  a window where a different paid gate could slip in first — and stops the
  run there.
- **The age gate's own timeout.** Fixed at `MAX_ATTEMPT_MS` (≈662 s, the
  client's own worst-case attempt bound, transport retries included) plus a
  downscale budget and a margin — round 1's `REQUEST_TIMEOUT_MS + 5s` (185 s)
  sat *below* a legitimately slow attempt's own ceiling. Only safe together
  with the queue-wait fix above; without it, a large run's FIFO wait alone
  could still exceed even this bound.
- **The near-duplicate claim.** `pdqClaims.ts`'s `PdqClaims`, a per-avatar
  map of pending (not-yet-stored) hashes, checked and claimed in one
  synchronous call (`checkAndClaim`) alongside the avatar's already-stored
  hashes (`input.photosByAvatar(avatarId)`'s own `qa.pdq`, read fresh on
  every check — its in-memory index already reflects a photo this same run
  stored moments ago, so no separate run-scoped list was needed for that
  half). No `await` sits between the comparison and the claim, so two
  concurrent checks on the same avatar can never both see "no duplicate yet"
  (pinned against both a known hash and a pending claim, at the exact
  boundary, in `pdqClaims.test.ts`). A claim is provisional, not a
  commitment (a `pass` here can still be retried or rejected by a later
  gate, e.g. age): `QaGate` itself gained an optional, first-class
  `releaseClaim?(avatarId, attemptId)` (round 2: replaces round 1's
  duck-typed `releasable()` helper and its `as` cast — no cast needed at any
  call site now), and `keepImage` releases every already-passed gate's
  claim in a `finally` wrapping the whole attempt — `runGates`, `addPhoto`,
  every branch — regardless of outcome, including a successful store. Round
  1 only released on a non-pass verdict, reasoning a stored photo's claim
  was harmless to keep (redundant with the library, "never needed again").
  That reasoning was wrong: the engine is one long-lived process, not a
  fresh one per run, so a leaked claim from an *earlier* attempt (a cancel,
  a gate that threw, `addPhoto` itself failing) stayed in memory and a later
  resume — in the very same process — could read it as a duplicate of a
  photo that was never actually stored, wasting a real paid attempt.
  Releasing unconditionally, always, closes every one of those leaks at
  once (confirmed against the reviewer's repros D, E and F: a throwing
  later gate, a stored-then-deleted photo, and a cancel mid-gate all now
  judge a resumed or later check fresh, never as a false duplicate) and
  costs nothing on the success path — `photosByAvatar` already carries the
  hash by then. `pdqGate.ts` also re-checks `input.signal.aborted` right
  before claiming (not just before decoding): a signal that fired in the
  narrow window while decoding was still resolving must never leave an
  orphaned claim whose owning attempt's verdict is about to be discarded by
  `runJob.ts`'s own abort race.
- **PDQ threshold.** `config.ts`'s `defaultQaConfig()`: 20 of 256 bits.
  PDQ's own documented "same image" range runs up to about 31; 20 sits
  inside it but short of the edge, so it still catches a provider handing
  back the same render twice without also catching two honestly different
  takes of one scene, which can legitimately land in the low 20s-30s on
  PDQ's own worked examples (the run's own *planner* varies location,
  outfit, shot and pose per slot — there is no seed in the image request
  itself, so two takes of a truly repeated scene can still render close
  together by chance). Not derived from this app's own duplicates — none
  has been seen yet — so `pdqGate.test.ts`/`pdqClaims.test.ts` pin the
  boundary exactly (20 a duplicate, 21 not, 19 a duplicate) so
  recalibrating it later is a deliberate, reviewed change to one constant.
- **PDQ image quality.** A flat or near-flat render (a solid moderation
  placeholder, a broken generation) hashes degenerately under PDQ — its DCT
  has no AC energy, so every flat frame hashes to the same value regardless
  of colour. `pdqGate.ts`'s new `gradientEnergy` (the sum of every adjacent
  pixel pair's absolute difference over the 64x64 frame) catches this before
  the hash is even computed: below `config.pdq.minGradientEnergy` (200,
  documented in `config.ts`) the image retries as a broken render, unclaimed,
  rather than being hashed and compared at all. `pdqPixels.ts`'s own
  downscale now also uses `scale=64:64:flags=area` (a box filter), closer to
  reference PDQ's own downscale than ffmpeg's bicubic default.
- **The age gate's own verdicts (unchanged from round 1).** Reuses
  `avatars/ageCheck.ts` as-is (no second implementation) for what still
  rejects: a moderation refusal, an empty or unreadable answer, or a clear
  no from `readAgeAnswer` — invariant 8's own rule, any doubt rejects, never
  retries. Aborting is still split by what was in flight: an abort while
  preparing the image (a local ffmpeg downscale, no different from pdq's own
  decode) propagates, so `runJob.ts`'s wrapper decides dropped vs. broken; an
  abort of the request itself (`input.signal`, or `beforeSend` refusing —
  see above) also propagates now, read the very same way.
- **The toggle off, with a real gate wired.** `engine.ts`'s `#runPhotos`
  filters `AGE_GATE_NAME` out of the run's own gate list whenever
  `plan.imageAgeCheck !== "on"` — pinned by a test (`engine.runs.test.ts`,
  "even with a fake age gate wired") that failed for the right reason before
  the fix: a wired age gate used to run unconditionally, regardless of the
  run's own mode. `#assertAgeGate`'s own pre-flight check
  (`AGE_GATE_UNAVAILABLE`) is unchanged: it still scans `EngineDeps.qaGates`
  by name, which is still where the real age gate lives. A second test
  (`engine.runs.test.ts`, "a run with the real createAgeGate wired") runs
  the actual production gate — not the local fake — through a real engine
  and a fake network, and pins that every photo is reserved, sent and
  settled under its own `:age` id with `qa.age` stored. A companion test
  there (network concurrency 1, a slow image) is a basic sanity check only
  — corrected after re-review (finding L3): a 60 ms image against the age
  gate's own ~682 s timeout cannot distinguish a fixed queue-wait bug from a
  still-broken one; `runJob.test.ts`'s own repro A (a 100 ms gate timeout
  against a 60 ms image, at pool size 1) is what actually pins finding 1,
  and its own repro B pins finding 3 (no send after another slot stopped
  the run).
- **The ffmpeg preflight.** No new explicit one for runs: `runJob.ts`'s own
  `loadMaster()` already downscales the master through ffmpeg before any
  paid image is sent, unconditionally, regardless of the toggle — a broken
  or missing ffmpeg is already caught there, for free, before a single
  request leaves. A *mid-run* ffmpeg failure (rare — the same binary just
  worked for the master) is caught by pdq's own decode step instead, which
  throws (systemic) and halts the run gracefully rather than crashing.
- **Deferred.** No dedicated pdq-vs-real-photo parity test (unlike the face
  gate's OpenCV parity check) — `src/core/pdq`'s own hash function is already
  tested in `src/core/pdq/pdq.test.ts` and treated read-only here; this
  task's own tests instead pin the gate's wiring (decode → hash → claim →
  verdict) with hand-built or synthetic frames. `Library.photosByAvatar`
  filters and sorts the whole avatar's photo list on every call (a pdq
  check now calls it on every paid image, on top of its existing callers) —
  fine at today's scale, worth an index per avatar if a library ever grows
  past roughly 10⁴ photos; no change made now.

Follow-ups (re-review, finding L5 — no code change made for this one):

- With the image age check on, an image's own reserve and its age check's
  own reserve are two SEPARATE `tryReserve` calls, made minutes apart (the
  image first, then — once it is back and passed pdq — the age check).
  Between them there is no guarantee the age check's own reserve will still
  fit: another slot's own attempt could fill the run's cap or the month's
  budget in between, refusing the age check with a `limit` (`ctx.limited`)
  after the image is ALREADY paid for and in flight. The paid image is
  then discarded and the slot stays open for a resume, which pays for a
  new image — money spent for nothing this slot could use.
  `avatars/candidateJob.ts` already solved the equivalent problem for
  candidate portraits: `Budget.tryHold` admits the image's AND the age
  check's worst case together, atomically, before either is sent, so an
  image is never bought without room already reserved for its own age
  check. `runJob.ts`'s own slot loop would need the same treatment — the
  image's own `generateImage` call would need to hold its own worst case
  plus (when the toggle is on) the age check's, before sending, not reserve
  and send immediately the way it does today.

- **The decode decision, with evidence.** The plan asked whether Electron's `nativeImage` is
  usable inside the engine's `utilityProcess`. Tested directly: a real `utilityProcess.fork()`
  child (not a stand-in) was made to `import("electron")` and inspect what it gets.
  `process.type` reports `"utility"`, confirming the child is genuinely a utility process, and its
  own `import("electron")` resolves to `{ default, "module.exports", net, systemPreferences }`
  only — no `nativeImage`, no `app`, and `globalThis.createImageBitmap` is `undefined` too. This
  matches the engine's own runtime rule (`runtime.test.ts` already flags `import { app } from

  is not reachable from the engine, by design and by measurement. Chosen: **(a) main decodes**.
  The alternative (b), decoding with the engine's own ffmpeg, was measured too before ruling it
  out: ffmpeg-decoded RGBA fed into the real gate gave cosine deltas of 0.000–0.016 against the
  nativeImage/OpenCV numbers on the 5 fixture frames (master 0.000000, impostor 0.000729 — both

  drift would quietly undermine the very analysis the threshold was chosen from. (a) was preferred

  Electron-only concern the engine cannot (safeStorage, dialogs, `studio-media://`), so answering

  - back: identity is never checked either, but a confidently detected face is suspicious (the
    model ignored "from behind"): `unexpected-face` → `retry`; no reliable face (the expected
    case) → `skipped-by-pose`, `pass`, no qa fields.
  - `multiple-faces` overrides every pose, front through back.
  A new boundary test was added to `policy.test.ts` (T7b's own "one step each side" pin, closing a
  real gap — only the exact-threshold case existed before): similarity `threshold - 0.0001` →
  `mismatch`, `threshold + 0.0001` → `match`.
- **Master embedding: once per avatar, not just once per run.** `faceGate.ts` caches the pending
  (or resolved) embedding promise in a `Map<avatarId, Promise<Float32Array>>` that lives for the
  gate's whole engine-process lifetime — a strict superset of "once per run" (an avatar's master
  is immutable once picked, invariant 9), so a second run of the same avatar in the same engine
  process reuses it too. Pinned by `faceGate.test.ts` (`embed()` called exactly once across 5
  checks of the same avatar) and by `engine.runs.test.ts`'s own real-gate test (once across 4
  slots' worth of checks through a real engine and run).
- **Master without a detectable face.** `FaceGate.embed()` throws by its own documented contract;
  `faceGate.ts` never catches that — it propagates uncaught. `runJob.ts`'s existing `checkFree`
  wrapper reads an uncaught throw from a free gate as `GateBroken` (systemic — every later image
  would hit the identical problem) unless the job was already cancelled, in which case it is
  `GateDropped` instead; neither path is new code, both already existed for "a free gate is
  broken" (e.g. ffmpeg missing). **Decision: the run is not refused up front.** The embedding is
  computed lazily, on the first candidate's own check, after that one image was already generated
  and paid for — not eagerly before any money is spent. This mirrors every other "gate is broken"
  scenario the codebase already accepts (a missing ffmpeg binary is discovered the exact same way,
  on the first attempt), and avoids adding a new `QaGate` lifecycle hook (today's contract has only
  `check`/`releaseClaim`) for one gate's own special case. The failed embed is cached too — a
  second photo of the same broken avatar fails identically without a second wasted decode+embed
  attempt.
- **Undecodable image vs. abort vs. a broken model.** `input.decodeImage` rejecting for an ordinary
  reason (not `input.signal.aborted`) is this one photo's own problem: `retry`. A rejection because
  the signal fired (the run's cancel, or the gate's own outer timeout in `runJob.ts`) propagates
  uncaught, exactly like the pdq gate's own decode failure, so `runJob.ts`'s own wrapper decides
  dropped vs. broken. A broken underlying `FaceGate.check`/`embed` (a model or ORT failure) also
  propagates uncaught — never turned into a `retry`, since the gate cannot judge ANY photo in that
  state, not just this one.
- **`FACE_GATE_UNAVAILABLE` — a new invariant, unlike the age gate's own toggle.** The face gate is
  never a Settings toggle; it is always required. If `studio/engine/main.ts` could not load it
  (missing/corrupt models, an ORT failure), a run must not silently store photos no identity check
  has ever seen. `Engine.#assertFaceGate()` (mirrors `#assertAgeGate` exactly, but unconditional —
  no `imageAgeCheck` parameter) refuses `runs.start`/`runs.resume` with the new `FACE_GATE_
  UNAVAILABLE` error code before anything is spent. Pinned in `engine.runs.test.ts` for both start
  and resume; also the reason the first local smoke run (above) failed loudly and cleanly instead
  of silently storing photos with no identity check.
- **Claim release / no interference with pdq.** The face gate makes no provisional claim of its
  own (`releaseClaim` is left undefined — `qa.test.ts`'s own contract test already covers "a gate
  with no `releaseClaim` is a harmless no-op"), so `runJob.ts`'s unconditional per-gate release
  costs it nothing. The real interaction risk is the OTHER direction: does the face gate's own
  retry leave the PDQ gate's claim dangling in a way that then wrongly flags the slot's next,
  byte-identical attempt as a duplicate of its own (never-stored) first try? Proven false with the
  real `createPdqGate()` wired alongside the adapter, through a real engine and run
  (`engine.runs.test.ts`): a slot's first attempt mismatches (face retries it), its second attempt
  — the network's own default handler returns the exact same bytes — still passes pdq and is
  stored, with both `qa.pdq` and `qa.faceCos` recorded. A second test pins the master-embed-once
  claim across 3 slots with genuinely different renders (avoiding pdq's own cross-slot duplicate
  check, which is a separate, correct behaviour, not a bug to route around), and a third pins
  ordering (`pdq` always runs, and reaches its own verdict, before `face` is ever called).
- **E2E composite approach, with numbers.** The packaged smoke's mock served no face at all before
  this task (an avatar master/candidate from a faceless mandelbrot render, run images from
  `distinctPattern.ts`'s checkerboards/stripes) — with the face gate now wired unconditionally,
  every front/three-quarter slot would have retried forever. `studio/scripts/facePool.ts`
  composites the real `master.jpg` fixture (the same one `parity.test.ts` already pins to the
  OpenCV numbers) onto each of `distinctPattern.ts`'s own PDQ-distinct backgrounds via ffmpeg's
  `overlay` filter, at a fixed 130×170 px patch centred at (35, 20) on the pool's 200×356 canvas —
  chosen empirically (a scratch experiment, then encoded as this module) to read as a plausible
  headshot framing. Measured, over the first 8 pool indices: minimum pairwise PDQ Hamming distance
  50 bits (comfortably over both the gate's own 20-bit threshold and the pool's own 40-bit proof
  bar — the varying background's own low-frequency structure dominates the DCT, not the fixed face
  patch), and every composite detected exactly one face with similarity 0.898–0.904 against the
  master (well clear of the 0.55 hybrid threshold). `distinctPattern.test.ts` extends its existing
  real-pipeline PDQ proof to these composites (same 40-bit bar, same ffmpeg `scale=64:64:
  flags=area,format=gray` decode) and adds a real-gate proof (real models, real Electron
  `nativeImage` decoding via the same harness `parity.test.ts` uses) that every composite passes
  as a `match`, similarity ≥ 0.55 — guarded by the identical CI-guard/`skipIf` pattern
  `parity.test.ts` already uses, never silently skipped in CI. `mockOpenRouter.ts` gained one new
  option, `faceFixture`, serving the fixture face for the avatar's master/candidate portraits and
  (with `distinctImages` also on) the composited pool for run images.
  `runPhotoRunKillResumeScenario` (the existing kill-and-resume scenario, already the only one
  that runs real photo runs end-to-end) turns it on and asserts, after the run finishes, that
  every generated photo's sidecar carries `qa.faceCos` — the asar/packaging proof that the models
  and ORT's WASM genuinely loaded and ran (`checkPackage`'s own asar-content check only proves the
  files are packaged, not that anything reads them; this is what proves they do). `RUN_POSES` was
  already `{ profile: false, back: false }` — no change needed there.
- **A pre-existing test-isolation bug found and fixed along the way.** `parity.test.ts`'s own
  "explicit wasmPaths" test sets `onnxruntime-web`'s module-level `ort.env.wasm.wasmPaths` and
  never restored it, leaking into every later test in the same `bun test` process that creates a
  face gate with the default (unset) `wasmPaths` — including this task's own new
  `distinctPattern.test.ts` test. Fixed with a captured-and-restored value in that test's own
  `finally`.

Follow-ups (not required for this task, noted for later):

#### T7b security review — decode moved into the engine, and money/correctness fixes

Two independent opus reviews (code and security) followed the wiring above. The security review
found the wiring's own "(a) main decodes" choice unacceptable and asked for a redesign; the code
review found several money-correctness bugs in the wiring itself. Both are recorded here.

- **The decode decision, reversed.** The wiring section above chose (a) — Electron's `nativeImage`,
  in the main process, over the new engine→main `EngineCall`/`MainReply` channel — because it kept
  parity with the spike's OpenCV numbers with no new subsystem. The security review rejected this:
  decoding untrusted, network-sourced image bytes (a paid image response, ultimately provider-
  controlled) with native Chromium decoders **in the privileged main process** — the one process
  that holds `safeStorage`, decrypts the API key, and owns every OS-level capability (dialogs,
  `studio-media://`, window management) — is not an acceptable place to run a decoder against
  attacker-influenced input, however unlikely a JPEG/PNG decoder RCE is in practice. A decode bug
  there is a bug in the process that can read the key; a decode bug in the engine's own
  `utilityProcess` (option, below) is a bug in a process that already only ever holds it for the
  duration of a request and cannot reach `safeStorage` at all.
  - **Options considered.** (b) A sandboxed renderer (`createImageBitmap` in a hidden
    `BrowserWindow`): rejected — a renderer process is a much larger, more privileged attack
    surface than a plain WASM module (it has a V8 heap with full JS, DevTools protocol access,
    potential IPC to main), and standing one up per decode (or keeping one alive) adds real
    complexity and its own crash/hang modes for no parity benefit over (c). (c) ffmpeg, already in
    the engine: already measured and rejected in the ORIGINAL wiring work (this doc, "The decode
    decision, with evidence") — cosine deltas of 0.012–0.016 against the OpenCV/nativeImage
    numbers, 12–16× over the gate's own 0.001 parity budget. (d) **A WASM JPEG/PNG decoder inside
    the engine itself** — chosen: no round trip to a privileged process at all, runs in the same
    memory-safe-by-construction sandbox (WASM linear memory) regardless of which process embeds
    it, and — the open question the original wiring work could not answer without trying it —
    unverified for parity until this task measured it.
  - **Parity evidence.** `@jsquash/jpeg` (mozjpeg WASM) and `@jsquash/png` (squoosh WASM), both
    Apache-2.0 (mozjpeg itself IJG/BSD/zlib, the squoosh PNG codec BSD-3-Clause — see each
    package's own `codec/LICENSE.codec.md`), loaded from disk with no `fetch` (a precompiled
    `WebAssembly.Module`, sha256-verified against the installed package version, handed straight to
    each library's `init()`). Measured **byte-identical, for opaque images, (sha256-exact on the
    decoded RGBA, not merely within a cosine tolerance) to Electron's `nativeImage`** on 10 real
    JPEGs — 4:2:0 (baseline), 4:4:4, grayscale, a P3/ICC-tagged variant, EXIF orientation 6,
    progressive at 1K and 2K, baseline 2K, and 16 MP (4096×4096, exactly at the new pixel cap) —
    and one PNG. Re-review N12: "opaque" is deliberate, not decorative — `nativeImage`
    premultiplies RGB by alpha for a pixel with real transparency (PNG only; JPEG has no alpha
    channel at all), this decoder does not, and every fixture measured (and every real photo the
    face gate ever sees — a generated or imported master, never translucent art) is opaque, so the
    claim was never actually tested against, or needed for, real alpha. The 5
    face-gate fixtures (`fixtures/images/*.jpg`) match the same way; `face/parity.test.ts` now
    decodes with this WASM path and asserts the sha256 match plus the original ≤0.001 cosine bar
    (measured: 0 drift, since the decode is proven byte-identical, not merely close). The reference
    hashes are committed (`face/fixtures/electronDecodeHashes.ts`), produced by
    `studio/scripts/generateWasmDecodeParityHashes.ts` from a real Electron `nativeImage` decode —
    parity.test.ts itself never runs Electron any more, so its own CI guard is no longer
    platform-limited (macOS/Windows only) either.
  - **Channel removal.** `control.ts`'s `EngineCall`/`MainReply`, `studio/main/imageDecode.ts` (the
    `nativeImageDecoder`/`handleImageDecodeCall` pair and its own test file), `engineHost.ts`'s
    `onCall` hook and its wiring in `main.ts`, and `engine/main.ts`'s `createDecodeImage`/
    `handleIncoming` port-message interception are all gone. The engine stays Electron-free — no
    exception for decode any more.
  - **Before/after decoding.** A JPEG/PNG magic-byte allow-list (`sniffImageMediaType`) and a
    header-parsed `MAX_DECODE_PIXELS` = 16,777,216 (`imageSize`, both from `library/media.ts`) run
    BEFORE any byte reaches the WASM decoder — never decode-then-check, which would let a crafted
    header-vs-payload mismatch allocate an unbounded buffer first. After decoding, the decoded
    width/height must equal the header's and `data.byteLength` must equal `width*height*4`; the
    output is tagged `"rgba"` (`TaggedPixels`'s existing tag — `toBgrImage` already handled this
    exact case, added when T6 anticipated a renderer's `createImageBitmap`, so no new pixel-format
    code was needed at all).
  - **Every failure is systemic, never a per-photo retry.** An unsupported format (the allow-list
    rejects anything but JPEG/PNG), a pixel-count overflow, or a decode that throws — these bytes
    already passed the pdq gate's own ffmpeg decode (gate order: pdq before face), so a WASM
    failure here means the decoder itself cannot handle this format/file, not that this one photo
    is bad. `faceGate.ts` no longer catches a candidate decode failure into a `retry` verdict (the
    old, Electron-era design, where an occasional `nativeImage` quirk really was plausibly a
    single-photo problem); it propagates uncaught, and `runJob.ts`'s existing `checkFree` wrapper
    already reads any uncaught gate failure as `GateBroken` — the run stops for a resume rather
    than looping through up to 3 paid attempts against a decoder that will never succeed on this
    input.
  - **Packaging.** `electron-builder.studio.yml`'s existing `files` list already includes
    `out-studio/**/*` and `package.json`, and since neither `@jsquash/jpeg` nor `@jsquash/png` is
    excluded (unlike `ffprobe-static`/`exiftool-vendored`/most of `onnxruntime-web`'s own `dist/`),
    their `node_modules/@jsquash/{jpeg,png}` trees ship inside `app.asar` automatically — no new
    `files` entries needed, and no `asarUnpack` (the two `.wasm` files are executable code, same
    reasoning as the face models' own WASM runtime). Installed size: `@jsquash/jpeg` 0.53 MB,
    `@jsquash/png` 0.22 MB (npm-reported unpacked sizes); the two codec `.wasm` files themselves are
    166,470 and 181,088 bytes. Negligible next to onnxruntime-web's own already-budgeted ~53 MB.
  - **H4 (Windows).** onnxruntime-web 1.30's wasm backend passes `wasmPaths.mjs` to a bare
    `import()`, which rejects a plain Windows OS path (`C:\...` is not a valid module specifier).
    onnxruntime-web's own wasmPaths pair goes through `decode/wasmPaths.ts`'s `wasmFileUrl`
    (`pathToFileURL(...).href`), pinned by its own test (`wasmPaths.test.ts`) asserting the
    `file://` form. Re-review N8 corrects an earlier claim here: the two JPEG/PNG codec `.wasm`
    files are NOT resolved this way — `realBackend.ts` reads them with a plain `node:fs/promises`
    `readFile(path)`, never handed to `import()`, so H4's own Windows failure mode does not apply
    to them; an unused `codecWasmFileUrl` that implied otherwise was removed.
  - **Recreating the WASM module after a fatal failure.** `@jsquash/jpeg`'s own `init()` may be
    called again with the same precompiled module to get a fresh emscripten instance;
    `realBackend.ts` does this when a decode's error looks like an emscripten abort/OOM (a best-
    effort message match), before rethrowing that attempt's own error. `@jsquash/png`'s
    wasm-bindgen wrapper gives no public way to force a fresh instance (its own `init()` is
    idempotent by design) — an acknowledged gap, not silently assumed away. It does not weaken the
    money-safety guarantee: every decode failure already stops the run rather than looping,
    whether or not a fresh instance would have succeeded on the next attempt.
- **The preflight.** No new, separate preflight was added: `studio/engine/main.ts`'s existing
  `loadFaceGate()` already IS the preflight — it loads the models AND builds the WASM decode
  backend together (the face gate cannot run without a working decoder either way, so the two now
  fail together) before the engine ever answers a command, and `#assertFaceGate` refuses runs
  without silently degrading. Money review **M3** found this preflight had no bound of its own: a
  hung ORT init (or a hung WASM codec load) could leave the engine's port handler stuck forever,
  never even answering a free command. Bounded now with `money/timeoutSignal.ts`'s
  `untilAborted`/`timeoutSignal` (25 s, `FACE_GATE_LOAD_TIMEOUT_MS` — re-review N14: below main's own
  30 s default command deadline, `engineHost.ts`'s `REQUEST_TIMEOUT_MS`, so a slow-but-eventually-
  successful load never leaves main's own first command timing out uninformatively while the
  engine would have answered shortly after) — the same shape
  `runJob.ts`'s own `loadMaster()`/`prepareGates()` use, chosen deliberately for that consistency.
  A load failure or timeout reaches `Engine` as the new `EngineDeps.faceGateLoadError`, so
  `FACE_GATE_UNAVAILABLE`'s own detail says why, not just that it happened.
- **The master-reference fix (M1/N1).** Money review: the face gate's master embedding was
  computed from `Library.loadReference()`'s own output — the ≤1024px JPEG downscaled specifically
  for the OpenRouter reference image. Measured drift: master embedding cos 0.9388 vs calibration,
  candidate shifts up to +0.029 — larger than the gate's own 0.001 parity budget, silently
  undermining the very threshold calibration this task's own 0.55/0.66/0.70 numbers rest on. Fixed
  with a new `Library.loadMasterOriginal()` — the same sha256/size check `loadReference()` runs,
  but skipping the downscale and returning the raw, original file bytes (unbranded: never sent to
  OpenRouter, so `LibraryReference`'s own contract does not apply).
- **H1 (master without a usable face) — the design reversed.** The wiring section above (see "Master
  without a detectable face") decided the embedding is computed lazily, on the first candidate's own
  `check()`, AFTER that image was already generated and paid for — and mislabelled that choice an
  "OWNER DECISION" in `faceGate.ts`'s own header comment. Money review H1 corrected both: it was the
  implementer's choice, not the owner's, and it spent money before knowing the gate could even run
  for this avatar. `QaGate` gains an optional `prepare(input: QaPrepareInput)` hook, called for
  every gate once per job (`runJob.ts`'s `work()`, right after `loadMaster()` and before the writer
  phase or any image request). The face gate's `prepare()` computes the master embedding there,
  from `loadMasterOriginal()`'s bytes (M1/N1); a failure ends the job failed with a new
  `MASTER_FACE_UNUSABLE` code, before a single request is sent — pinned: 0 POSTs (no writer, no
  image) on both `runs.start` and a resume.
- **H2 (the embedding cache).** The cache is now keyed by avatarId + the master bytes' own sha256
  (never avatarId alone), and only a *successful* embedding is kept — a rejected computation is
  evicted from the cache immediately, so a resume after a transient failure (a decode hiccup, not
  "this avatar's master genuinely has no face") gets a fresh attempt instead of being stuck with a
  permanently poisoned cache for the rest of the engine process's life. The shared computation
  itself runs against an internal `AbortController` nothing ever aborts, independent of any one
  caller's own signal — a caller that gives up waiting (its own timeout, the job stopping) rejects
  its own wait without killing the computation for another caller, or a later job's `prepare()`,
  still waiting on the very same one.
- **M4 (gate order).** The production QA gate order (`pdq`, `face`, `age`) — already correct in
  `engine/main.ts`'s own wiring — moves into its own tested function,
  `runs/productionGates.ts`, so the rule has one home instead of being re-derived by inspection.
  `engine.runs.test.ts`'s own gate-list test helper used to append its auto-inserted fake face gate
  at the end of whatever a test's own `qaGates` array was, silently putting it AFTER a test's own
  age gate in several existing tests — backwards, since money must never be spent by the (only)
  paid gate before every free gate, face included, has had its say. Its own "pdq runs before face"
  test used to only prove pdq's `check()` ran first on a single, non-duplicate image, never its own
  title's claim; it now seeds a real prior photo whose stored pdq hash matches every attempt's own
  generated bytes, so the real gate genuinely retries every attempt as a duplicate and the face
  gate is provably never reached.
- **M5.** `SettingsScreen.tsx`'s face-similarity row and its own code comment said the gate "will
  appear along with photo runs" / was "not wired into the job pipeline yet" — stale now that this
  task actually wired it in; fixed (the scenes/image-model rows above it keep their own
  "появится вместе с фото-ранами" hint unchanged, since T5b genuinely is not wired yet).
- **L7 (cosine clamp).** `faceGate.ts`'s `qaOf` now clamps `faceCos` to `[-1, 1]` — the photo
  schema caps it there (`schemas.ts`); an overflow by a rounding step (observed possible at
  `1.0000000000000002`) would otherwise throw in `Library.addPhoto` and stop the run.
- **L9 (E2E).** The packaged smoke's run scenario (`runPhotoRunKillResumeScenario`) only ever
  exercised the always-matches path. `mockOpenRouter.ts`'s new `faceMismatchAt` option serves a
  genuine "no face detected" image (measured directly against the real gate — a composited
  different-person's face does not reliably land in the gross-drift range: the fixture impostor
  composited at the pool's own patch size scores 0.647, still a `match` under the hybrid policy;
  "no face" is the only deterministic clear-failure available) at exactly one of the pool's 48
  indices; the scenario now asserts at least one `qa-retry` in the run's journal, the exact stored
  photo count (not just "some photos"), and `qa.faceCos >= 0.55` on every photo. The mock's images
  are real JPEG now, not PNG (production's own image model returns JPEG; the single-fixture
  fallback path was already serving a real JPEG file mislabelled `image/png` under the misleading
  name `faceFixturePng` — renamed to `faceFixtureBytes` and the `media_type` now matches the actual
  bytes in every mode). This is what actually exercises the engine's WASM JPEG decode path in the
  packaged smoke, not only its PNG one; the kill -9 + resume scenario and its no-double-send proof
  are unchanged.
  - **A real bug the E2E build caught, twice.** (1) `bun test` and every manual `bun run` script
    resolved `import("@jsquash/jpeg/decode")` fine (bun's own lenient resolver), but the packaged
    engine — real Node, and neither `@jsquash` package declares a package.json `exports` map —
    failed to load it at all (`Cannot find module ... Did you mean to import ".../decode.js"?`):
    ESM `import()` never auto-appends an extension the way `require()` does. Fixed with the
    explicit `.js` extension `realBackend.ts` now uses; `bun test` alone would never have caught
    this, only the actual packaged/unpackaged build running under Electron's real Node did. (2) The
    first version of `faceMismatchAt` was a boolean hard-coded to pool index 0 — the run's own
    `/images` counter is shared with the avatar's own candidate-portrait generation, which runs
    BEFORE the run and always requests exactly 4 images first, so index 0 became one of the 4
    CANDIDATES, not a run slot's attempt, and `avatars.pick` (which always picks `candidates[0]`)
    made a faceless image the run's own MASTER — `prepare()` (H1) correctly failed the whole job as
    `MASTER_FACE_UNUSABLE` before any slot ever ran, and the smoke script's own `waitFor` for run
    progress spun for 60 s finding nothing, then errored. Fixed: `faceMismatchAt` is now an
    explicit pool index, and the smoke script passes 4 (past the fixed candidate count) so the
    mismatch lands on the run's own first slot attempt instead.
- **EXIF orientation.** Electron's `nativeImage` ignored it (decoded raw sensor-order pixels,
  confirmed directly: a 1K JPEG with EXIF orientation 6 and its orientation-free twin decode to the
  identical sha256); the renderer, showing the same bytes to the owner, applies it via CSS/canvas
  as browsers do. Decision (smallest safe option): keep scoring raw, un-rotated pixels — this is
  the exact behaviour the calibration numbers (0.55/0.66/0.70) were measured against, and mozjpeg's
  own default (`preserveOrientation: false`) already matches it with zero extra code, confirmed by
  the parity measurement above (the EXIF-6 fixture decodes byte-identical to its EXIF-free twin
  under both decoders). Documented, not fixed: a future change to normalize orientation before
  storing would need re-calibration, not just a decode-side tweak.
- **Deviation from the plan's "heavy inference in a worker_thread" (follow-up T7c).** The fixed
  decisions table (top of this doc) planned "heavy inference in a `worker_thread` inside the
  engine"; inference still runs on the engine's own main thread, unchanged from the original
  wiring. Measured (this task, `onnxruntime-web`'s wasm backend, 4 threads, on this machine):
  inference alone (no decode) 25–31 ms at 1K (720×1280), 69–81 ms at 2K (1536×2752) per check, ~317
  ms total for 4 concurrent 2K checks, resident memory up to ~1.25 GB. With the new WASM decode
  included: ~32–37 ms at 1K, ~101–114 ms at 2K per check (decode + inference together), ~445 ms for
  4 concurrent 2K checks, resident memory up to ~1.7 GB. All measured synchronously on the engine's
  own event loop — a `worker_thread` would remove this from blocking other engine work (money
  writes, other gates' free work) during a large run's concurrent slots, at the cost of a
  structured-clone or transfer of the decoded pixels across the worker boundary. Left as `worker_thread`
  is a real design change, not a bug fix, and out of this task's own scope: T7c.
- **2K is uncalibrated.** The owner's threshold calibration (0.55/0.66/0.70, this doc's T7b row)
  was measured at 1K, the app's own default resolution; 2K's own true/impostor score distribution
  has not been separately measured. The numbers above (2K inference/decode timing) are performance
  only, not a calibration claim. Re-review, MUST FIX 1: 2K (1536×2752, long side 2752) is now
  downscaled by `normalizeForFacePipeline` to 1280 on its long side before detection — the SAME
  geometry 1K was calibrated at, not a separate, larger one — so the calibration's own applicable
  range is arguably wider than "1K only" now, but this is reasoning, not a measurement: still to be
  measured by the canary if/when 2K runs are actually used, the same as before this task.

#### T7b re-review (opus, round 2) — normalization, the master source rule, the memory lane

A second independent review (code and security) followed the fixes above. It confirmed H1/H2/H3/H4
(code) and H1/M1 (security) fixed, parity independently reproduced (22 inputs byte-exact, the
committed hashes genuine), the old decode channel fully removed — and found one HIGH regression
plus smaller items, recorded here.

- **The normalization decision (MUST FIX 1).** The face pipeline fed YuNet the image at whatever
  resolution the source happened to be, with no normalization to the geometry the owner's
  calibration was measured at. Measured (the reviewer's own sweep, reproduced here): a 422 px face
  scores 0.885, 504 px 0.758, ~630 px is not detected at all — detection fails on LARGE faces, not
  only small ones, because YuNet's own anchor sizes assume a face that fits the calibrated
  geometry; a 12 MP phone import or a 2K close-up render both produce faces well past that size.
  Fixed: `face/normalize.ts`'s `normalizeForFacePipeline` downscales every image entering the
  pipeline (the master in `prepare()`, every candidate in `check()`, `gate.ts`'s own two call
  sites) to a long side of at most `FACE_PIPELINE_MAX_SIDE` (1280 px) before
  detection/alignment/embedding — a strict no-op (the exact same object, never a copy) at or below
  the cap, so every calibrated size (1K renders 720×1280, generated masters 864×1152) never enters
  the resize path at all and `parity.test.ts`'s byte-exact assertions are untouched (pinned:
  `normalize.test.ts`'s own no-op tests). Area/box-average downscale, not nearest-neighbour or
  bilinear — OpenCV's own documented recommendation for shrinking (`INTER_AREA`), chosen to avoid
  the aliasing nearest-neighbour would introduce at exactly the fine detail YuNet/SFace read;
  every source pixel is visited exactly once, pure TypeScript, no new dependency. Verified against
  real models: a 3024×4032 (12 MP) and a 4096×4096 (16 MP) master both detect and embed correctly
  post-normalization (measured similarity 0.90–0.92 against themselves through a real composite),
  where they previously either scored far below threshold or were not detected at all.
- **The master source rule (MUST FIX 2, N1 — a HIGH regression from the M1 fix).** `prepare()`
  always embedded `loadMasterOriginal()`'s raw bytes, but the WASM decoder only handles JPEG/PNG
  (`decode/wasmDecode.ts`'s own allow-list) while import accepts WebP up to 16 MP
  (`importStaging.ts:26`) — every WebP-imported avatar's runs failed `MASTER_FACE_UNUSABLE`
  forever, on a perfectly usable master. The rule now: embed the ORIGINAL stored master file when
  it is JPEG/PNG (M1/N1's own fix stays — never the OpenRouter-bound downscale for those); fall
  back to `loadMaster()`'s own ≤1024px JPEG reference (`QaInput.master`, previously computed but
  unused by `prepareGates()`) when the original is any other format. Engine tests, real models +
  real decoder (`engine.runs.test.ts`, "re-review N1/normalization"): a 864×1152 JPEG (the
  calibrated control), the same portrait as WebP, at 1296×1728 (×1.5) and at 3024×4032 (12 MP) all
  complete without `MASTER_FACE_UNUSABLE`; the JPEG case is separately pinned to still embed from
  the ORIGINAL bytes, not the fallback reference.
- **N3 (failure classification).** `MASTER_FACE_UNUSABLE` used to catch every `prepareGates()`
  failure, but its own Russian text tells the owner to do something about the master — wrong advice
  for a decode/library/ORT problem, or the function's own timeout, none of which mean the master
  itself is unusable. A dedicated `NoFaceInReferenceError` (face/gate.ts) is now the ONLY thing
  `prepareGates()` maps to `MASTER_FACE_UNUSABLE`; everything else ends `INTERNAL` instead, the same
  systemic shape a broken gate mid-run already used. The Russian text was reworded: no promise of a
  replace-master action the app has no button for; suggests a new avatar or a re-import instead;
  keeps «Ничего не потрачено.» (still true).
- **The memory lane (N5).** ORT's WASM heap grows with the largest input it has ever seen and
  never shrinks — measured (the reviewer's own bench, reproduced here): +270 MB at 4.2 MP, +950 MB
  at 12 MP for one decode+inference; several free gates running concurrently (the run's own CPU
  pool) multiplied that peak by however many overlapped. `createFaceQaGate`'s `check()` now
  serializes its own decode+inference through a small FIFO mutex (`runs/faceGate.ts`'s
  `createMutex`) — never the master-embedding cache lookup, which stays cheap and already
  deduplicated (H2). Throughput is unaffected: ORT's WASM inference already runs synchronously on
  the engine's one event loop regardless of how many `check()` calls are in flight: this only stops
  them queuing their own decode+inference memory on top of each other. A waiter whose own signal
  aborts while queued rejects at once and frees its slot, never blocking whoever is behind it
  (pinned: two concurrent checks never overlap; a cancelled waiter does not lock out a later one).
- **The final fix round (re-review, round 2): B1, B2, and the CMYK master
  fallback.** Three more bugs found and fixed in this same area, each with
  its own test.
  - **B1 (the mutex's own exclusion, `commit 3dcca71`).** The first version
    of `createMutex`'s aborted-waiter handling released its own queue slot
    the moment a WAITING caller's signal aborted — but that slot is exactly
    what a LATER waiter is chained onto, so a cancelled middle waiter let
    whoever was queued behind it acquire the lock while the original holder
    was still running (repro: holder H running, A queued then cancelled, B
    queued behind A — `start H, start B, end B, end H`, two holders at
    once). Fixed: a cancelled waiter's own slot only resolves once the
    holder it was actually waiting on finishes, never at the moment of its
    own cancellation. Separately: a caller that already HOLDS the lock can
    itself hang forever (a real decode/ORT deadlock) — its own signal
    aborting now releases the lane too (like `CpuPool`'s own shape), with a
    known, accepted trade-off: `body()` keeps running as an abandoned
    "zombie" computation nothing here can stop, so it can still overlap the
    very next check that acquires the lock after a timeout (the same
    limitation the master-embedding computation already has, H2). Pinned in
    `faceGate.test.ts` ("B1: a waiter cancelled while queued BEHIND an
    active holder…", "B1: a hung holder released by ITS OWN signal…").
  - **B2 (a slow embedding evicted mid-flight, `commit 687f0f5`).** N11's own
    eviction timer can fire while a genuinely slow (not hung) master-
    embedding computation is still pending — a job cancelled mid-flight, or
    a resume reusing the same pending promise — and the computation then
    succeeds anyway: the caller's own `prepare()` resolves correctly, but by
    then the cache entry it read from is already gone, so a later `check()`
    finds nothing and the run breaks (`GateBroken`) after a paid image, for
    no real reason. Fixed: `embeddingFor()` re-installs a settled cache
    entry on resolve, but only if the avatarId's own slot is still empty or
    still holds the same sha256 — never clobbering a genuinely newer or
    different preparation that has since taken over. Pinned in
    `faceGate.test.ts` ("B2: a SLOW (not hung) computation evicted
    mid-flight, then resolving, still leaves check() a usable entry").
  - **The CMYK master fallback (`runJob.ts`'s `prepareGates()`, `commit
    7e98cb4`).** `masterOriginalFor()` only sniffs the FORMAT (JPEG/PNG vs.
    not, N1's own fix); a real JPEG/PNG master can still fail to DECODE — a
    CMYK colour space is the concrete case found (ffmpeg and the import path
    tolerate it, the WASM decoder does not). A genuine "no face" is never
    retried (the reference is the same photo, just smaller — it cannot have
    a different face), and neither is a failure already against the
    reference itself (nothing left to fall back to); any other decode
    failure against the original now gets exactly one retry against
    `loadMaster()`'s own ≤1024px reference, already downscaled to a format
    the decoder is known to read, under the SAME signal/timeout budget —
    never a second, independent deadline. Pinned against a real CMYK
    fixture (`face/fixtures/images/master-cmyk.jpg`, `engine.runs.test.ts`).
    2b whole-slice review (this session): that same fallback used to still
    fire once `signal` had already aborted (a cancel, or `prepareGates()`'s
    own timeout) — wasting a real embedding computation nothing here can
    actually stop (B1's own zombie trade-off, above) on work whose result
    would only be thrown away; fixed with a guard rethrowing instead
    (`runJob.test.ts`, "a cancel during prepare must not start the CMYK/M1
    fallback's own reference embedding a second time").
- **N10 (the cache's own key, used consistently).** `check()` used to look up the cached master
  embedding by avatarId alone, trusting whatever was cached "right now" — in this same long-lived
  engine process, that could be a stale or differently keyed preparation. `QaInput` now carries
  `masterSha256` (`Context.masterSha256`, recorded once by `prepareGates()`), and `check()` verifies
  the cache entry's own sha matches it before trusting it.
- **N11 (a computation that never settles).** A master-embedding computation that hangs (a real
  decode/ORT hang, not merely a caller giving up) used to stay cached forever — eviction only ran on
  rejection. `EMBEDDING_COMPUTE_TIMEOUT_MS` (30 s) now evicts it regardless of whether it ever
  settles, so a later job (a resume, a new run) gets a fresh attempt instead of repeating the exact
  same hang forever.
- **N4 (CI).** The canary job (ubuntu, weekly schedule) never fetched the face models, so its own
  `parity.test.ts` guard — no longer platform-limited once decode stopped needing Electron — turned
  the scheduled run red every week. Fixed: the same model cache + fetch steps the `build` job
  already has.
- **N6/N7 (decoder robustness).** The fatal-wasm-failure detector's own regex missed emscripten's
  real "Aborted(OOM)" message (a word-boundary bug); also checks `error instanceof
  WebAssembly.RuntimeError` directly. `createRealDecodeBackend()` now decodes one tiny embedded
  JPEG and PNG at load, so a broken codec fails there (`FACE_GATE_UNAVAILABLE`) rather than mid-run.
- **N14 (the load bound vs. main's own deadline).** `FACE_GATE_LOAD_TIMEOUT_MS` (60 s) exceeded
  main's own default command deadline (`engineHost.ts`'s `REQUEST_TIMEOUT_MS`, 30 s) — the engine
  answers nothing until `loadFaceGate()` resolves, so a slow-but-eventually-successful load could
  still be running when main's own first command already gave up uninformatively. Lowered to 25 s
  (normal load is ~1 s).
- **N8 (dead code / stale docs).** An unused `codecWasmFileUrl` (the two codec `.wasm` files are
  read with a plain `readFile(path)`, never handed to `import()` — H4's own Windows failure mode
  never applied to them) was removed rather than left unexercised; the plan's own earlier claim that
  they load by URL was corrected above. `wasmDecode.ts` named a `wasmDecode.parity.test.ts` that was
  never created (the real one is `face/parity.test.ts`); `engineHost.test.ts` carried a leftover
  "…, continued" describe split from removing the old decode channel, merged back into one.
- **N12 (the parity claim's own scope).** "Byte-identical" is true for opaque images —
  `nativeImage` premultiplies RGB by alpha for a pixel with REAL transparency (PNG only, JPEG has
  no alpha channel); this decoder does not. Every fixture measured (and every real photo the face
  gate ever sees — a generated or imported master, never translucent art) is opaque, so the claim
  was never actually tested against real alpha, and the wording now says so.
- **N13 (housekeeping).** Short comments now justify `realBackend.ts`'s two `as` casts (the
  upstream `.d.ts` predates the packages' own runtime support for a precompiled
  `WebAssembly.Module`; every value is re-validated downstream regardless); `@jsquash/jpeg` and
  `@jsquash/png` are pinned to exact versions in `package.json` (their sha256 was already pinned, so
  a floating range bought nothing). Third-party notices: neither Studio nor the uniquifier has an
  existing NOTICES/third-party-licenses mechanism anywhere in this repo — the libjpeg-turbo/IJG
  acknowledgement this task's own license terms call for (see `node_modules/@jsquash/jpeg/codec/
  LICENSE.codec.md`) has nowhere to go yet. Reported rather than inventing one: this needs an
  owner decision on where such notices should live (an About screen, a NOTICES.md, `extraResources`
  in the installer, …), not a unilateral choice made here.
- **N9 (test coverage).** Exactly `MAX_DECODE_PIXELS` (4096×4096) accepted and one pixel row over
  refused, for both JPEG and PNG headers (`wasmDecode.test.ts`); the real backend (not the fake one
  most tests use) on a corrupt JPEG, a truncated one, a real WebP, and a header patched to claim a
  pixel count over the cap without touching the scan data, none hanging or crashing

## Stage 2 backlog

Known gaps and follow-ups, not blocking the slices above, previously tracked only in a private note. Recorded here so they survive past this session.

- **T7c — the face gate in a `worker_thread` (done).** The face gate's heavy work (image decode, normalization, YuNet, SFace) moved off the engine's event loop into one worker thread inside the engine utilityProcess, the plan's original decision (the T7b reviewers measured 25–31 ms per 1K check, 69–81 ms at 2K, ~100 ms decode + inference per 2K image, all blocking the engine, and a synchronous WASM computation could be interrupted neither by the gate timeout nor by a cancel). Decisions:
  - **Shape.** `studio/engine/face/worker/`: `faceWorker.ts` (the worker: loads ORT + both models with a sha256 check + the codec WASM, then decode → normalize → detect → align → embed/check, one request at a time), `protocol.ts` (zod schemas for `workerData` and both message directions — validated at both ends; a message outside the protocol kills the worker), `workerGate.ts` (the engine side: `createWorkerFaceGate`, owns the worker's whole life), `spawn.ts`. The engine sends the encoded bytes and receives a small verdict (`check`) or the 128-float embedding (`embed`, the master); the QA adapter (`runs/faceGate.ts`) hands it bytes and the run's own signal, so the engine-side `decodeImage` plumbing (`QaInput`, `QaPrepareInput`, `RunJobDeps`, `EngineDeps`) is gone. The bytes are COPIED once and the copy's buffer is transferred (structured-clone-free): the caller still needs its own bytes to store the photo, and a transferred buffer would be detached.
  - **Lifecycle.** The worker is spawned lazily by `workerGate` (`main.ts`'s `loadFaceGate()` calls `start()` as the preflight, bounded by the same 25 s `FACE_GATE_LOAD_TIMEOUT_MS`, below main's 30 s command deadline: a load failure or timeout terminates the worker and reaches `EngineDeps.faceGateLoadError` → `FACE_GATE_UNAVAILABLE` with its detail). The lane is a FIFO of waiters removed by identity (the T7b B1 hazard cannot arise; a waiter cancelled while queued leaves at once and never touches the worker busy for someone else). A cancel or timeout of the computation IN FLIGHT terminates the worker, and the lane is released only once its `exit` event has fired — so two computations, or two workers, never overlap (pinned by counting live workers at every spawn). The next check lazily spawns a fresh worker (~0.2 s). A worker that crashes, exits, sends something outside the protocol or fails to load rejects the call with an ordinary Error — the same systemic classification as before (`GateBroken`/`INTERNAL`, never a paid retry); a failure the worker reports itself (an undecodable image) rejects likewise but leaves the worker alive; a reference with no face is `NoFaceInReferenceError` (now in `face/noFaceError.ts`). An idle worker is terminated after 60 s (`FACE_WORKER_IDLE_RECYCLE_MS`; the recycle takes the lane, so it never overlaps a new worker).
  - **Master embedding (H2/N11/B2).** `prepare()` goes through the worker too; the avatarId + sha256 cache, eviction of a rejected or never-settling computation and the B2 re-install are unchanged. What changed: the shared computation now runs against its own `timeoutSignal(embeddingComputeTimeoutMs)` (30 s) instead of a never-aborted controller, so a hung embedding TERMINATES the worker at the bound instead of occupying the lane forever; a caller giving up still does not abort it (H2). The consequence, deliberate: a computation that would have outlived 30 s is killed rather than left to finish (B2's "slow but succeeding" case can now only come from a backend that ignores its signal, which is how its unit test drives it).
  - **Packaging.** `engine/faceWorker` is a separate entry in `electron.studio.vite.config.ts` (emitted as `out-studio/engine/faceWorker.js` plus a shared chunk); `main.ts` resolves it as `new URL("./faceWorker.js", import.meta.url)` and everything the worker loads (model paths, `node_modules`, ORT `file://` wasm paths, the config) travels in `workerData` — the worker resolves no path. It loads from inside `app.asar` (no `asarUnpack`) and works the same on Windows (file URL, not a joined path). `runtime.test.ts` now walks the worker entry too (Electron-free). `bundleChecks.ts`'s `faceWorkerProblems` and the production smoke fail the build checks when the worker entry is missing/empty, is not a worker thread, imports `electron`, when the engine no longer spawns it by that URL, or when a chunk it imports is absent (in the build directory and in the asar); the asar check also requires it not to be unpacked; the packaged E2E's `qa.faceCos` proof now also proves the worker starts from inside the asar.
  - **A runtime fact the design rests on.** Node/Electron's `worker.terminate()` ends a worker stuck in a synchronous loop within a millisecond; Bun's never settles on one (and on an already-exited worker). So the unit tests hang a scripted worker asynchronously (`face/testing/scriptedFaceWorker.ts` speaks the real protocol without inference) and the smoke proves the synchronous case on Electron's own runtime (`ELECTRON_RUN_AS_NODE`, unpackaged targets). Real-worker tests (real models) share one gate per test process (`sharedRealFaceGate`): a dozen workers spawned across `bun test`'s single process ran it out of address space ("RangeError: Out of memory" while a worker loaded, full run only).
  - **Measured** (this machine, `studio/scripts/faceWorkerBench.ts`, Bun, warm; the bench is the reproduction): four 2K (1536×2752) checks issued at once — in-thread (how it ran: serialized behind the old mutex) ~235–240 ms wall with the event loop blocked for all of it (largest timer gap 235–240 ms); through the worker ~237–277 ms wall, largest gap 5–21 ms. A 12 MP (3024×4032) master embed: in-thread gap 115–183 ms; worker 5 ms. Throughput is unchanged (one computation at a time either way).
